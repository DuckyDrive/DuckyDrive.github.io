Section 13Security, privacy & media

The frontend is public and the backend is shared. Anything the browser can be tricked into sending is treated as hostile.

Headers

Content-Security-Policy with default-src 'self', explicit allowlists for fonts and the API origin, frame-ancestors 'none' and object-src 'none'; plus HSTS, nosniff, a strict referrer policy and a permissions policy disabling camera, microphone, geolocation and payment. The main application's CSP is scoped to its own routes so a game deployment cannot weaken it.

Data minimisation

Collected: username, password hash, optional passkey/TOTP material, optional GitHub link, profile content the user chooses to add, and the activity needed for features they enable. Not collected: email (unless a future decision makes it optional), real name, phone, address, precise location, IP beyond short-lived hashed rate-limit keys. No advertising or tracking scripts.

Incident response

Detect (error-rate and auth-failure alerts, webhook and deployment failures, abuse reports) → contain (revoke sessions, disable an endpoint by flag, read-only or maintenance mode, rotate a leaked key) → assess scope and obligations → eradicate (patch, rotate, invalidate) → recover (restore, verify, re-enable gradually) → review (written timeline and follow-ups). The Owner is notified of any security incident, and key rotation is rehearsed rather than improvised.

Section 14Performance, accessibility & QA

MetricTarget on a mid-range phone
Largest Contentful Paint≤ 2.5 s

Initial JS per route≤ 180 KB compressed

Route-level code splitting, intent-based prefetching, artwork at display size with reserved aspect boxes, skeletons sized to content, and no client-side analytics blocking. Public catalogue reads come from materialised views; pagination caps at 50 with 24 default; queries time out at 5 s; realtime allows one channel per room with presence throttled to one update per 30 s. Background work — discovery scans, trending, snapshots, reconciliation — runs on a queue with concurrency limits.

Caching: immutable hashed assets for a year, short-lived HTML, 30–60 s stale-while-revalidate for public reads, never shared caching for user-specific data. If the backend is unreachable, cached catalogue pages load with a "may be out of date" banner, chat falls back to polling, and GitHub failures show fields as unavailable rather than blanking pages.

Accessibility

Keyboard operable everywhere with a skip link and visible focus; focus trapped in dialogs and restored on close; 4.5:1 body contrast and 3:1 for large text and UI boundaries; one h1 per route with ordered headings; labelled form fields, not placeholder-only; aria-live announcements for counts and errors; reduced motion honoured; 44×44px targets; usable at 200% zoom on a 375px viewport; alt text for meaningful images and text summaries for charts. Games are outside platform accessibility guarantees, but the catalogue states when a game's support is unknown.

Required negative tests

  1. A member attempts an admin action → 403.
  2. An Administrator attempts an Owner-only action → 403.
  3. An Administrator without repository access edits a game → 403.
  4. A contributor loses GitHub access → next edit fails, discovery scope shrinks.
  5. A private repository is discovered → withheld, never listed.
  6. A malformed metadata file is found → error recorded, not published.
  7. A webhook is replayed → no-op.
  8. A deployment fails → no public release entry.
  9. A DLES action is duplicated → rejected by idempotency.
  10. A game server disconnects during an event → tracked, restore attempted.
  11. A user awards themselves XP or a duplicate reward → rejected by the ledger.
  12. A user uploads an image to chat → rejected by the schema, not just hidden.
  13. A user requests another user's private collection or DM → 403, never an empty success.
  14. A user follows a project and it updates → no notification is created.

Definition of done: requirements and permissions implemented, RLS tested for all roles, error states present, keyboard and screen-reader paths work, negative tests pass, audit entries written where required, and no confirmed decision contradicted.

Section 15CI/CD, Freebuff & operations

RepositoryPurposePages target
DuckyDrive/DuckyDrive.github.ioMain application (and this specification)https://duckydrive.github.io/
DuckyDrive/<game-slug>One repository per gamehttps://duckydrive.github.io/<game-slug>/

Naming is lowercase and hyphenated, matching the declared slug exactly. The slug is reserved in the database before the repository exists, so two games cannot claim one path.

Branching and checks

main is protected; work happens on short-lived branches; every change opens a pull request describing intent and risk. Required checks: typecheck, lint, unit and integration tests, metadata validation for game repositories, build, output-path validation, and an accessibility smoke test for the main app. At least one approval is required, squash merge keeps history readable, and release tags come only from main.

Deployment

The main app builds for its Pages base path, validates that no asset references an absolute root path, publishes atomically, then runs a post-deploy smoke test fetching the landing page, a project page, the manifest and the API health endpoint — failing the workflow if any is not 200 with expected content. Games follow the same shape into their own folder through a reusable workflow. Staging is a separate Pages environment with its own Supabase project. Rollback redeploys the previous known-good commit; database changes roll back by compensating migration, never by restoring a snapshot over live data.

Secrets

Public build variables hold only the API base URL, Supabase URL, anon key and safe feature flags. CI holds deployment tokens. Edge functions hold the service role, GitHub App key and webhook secret. No secret in a public repository, no secret in a client bundle, a rotation runbook for every key, and a build that fails if a high-entropy string appears in a public artifact.

Freebuff workflow

  1. Read this specification before making product decisions.
  2. Work inside the relevant repository and follow its instructions.
  3. Generate and maintain duckydrive.json for new games, including in a new chat, filling only known fields.
  4. Add SDK or DLES integration only when asked, within declared capabilities.
  5. Run the project's checks and report what passed and what did not.
  6. Explain changed files and risks in plain language.
  7. Never publish or deploy without the agreed review and approval flow.
  8. Keep diffs reviewable and avoid destructive rewrites.

The metadata rule is a standing workflow instruction, not something the user repeats per project.

Monitoring, backup and recovery

Alerts on error rate above 2% over five minutes, auth-failure spikes, any deployment failure on main, webhook backlog above 100 or older than ten minutes, sync staleness beyond 30 hours, realtime disconnects above 10% in ten minutes, database saturation above 80% and abuse signals at three times baseline. Dashboards are operational and staff-facing only.

Daily database backups with point-in-time recovery where the plan allows, weekly verified restores into a scratch project, storage backed up on the same schedule, and source backed up by GitHub itself. Targets: RPO 24 h (1 h with PITR) and RTO 4 h at prototype scale. Free-tier honesty: if the plan lacks PITR or long retention, the real RPO is stated rather than assumed. Restore drills run quarterly with counts compared and logins verified. Maintenance mode serves a maintenance page, keeps games reachable, blocks writes, keeps staff login available and is an audited action.

Section 16Roadmap, risks & appendices

The MVP is the smallest version that is genuinely useful without compromising the architecture: unified shell with catalogue browsing, project pages, GitHub discovery with validation, game launching from separate deployments, accounts with favourites and follows, ratings and comments. Chat, DLES, XP and the Admin Panel follow — the data model already accounts for them, so they are additions rather than redesigns.

What must not start early

  • Chat before its moderation tooling exists.
  • DLES before capability manifests and the SDK handshake are proven.
  • Leaderboards before the XP ledger is append-only and capped.
  • Any per-game deployment before slug reservation and path validation exist.

Open items needing the Owner

Most decisions are defaulted so delivery is not blocked. Four are deliberately not defaulted: whether an optional email is ever added, whether group DMs are in scope, the paid tier chosen when free limits are reached, and the final visual sign-off on the proposed design tokens.
