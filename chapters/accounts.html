Chapter 05 · Sections 10-11

DuckyDrive ID, Profiles & Privacy

One account works across the DuckyDrive ecosystem. No email address is required or collected as a mandatory field.

5.1 Identity model

DuckyDrive ID is the central identity. It consists of:

  • a canonical user id (UUID) that never changes and is what every foreign key references,
  • a username (unique, case-insensitively, changeable under cooldown),
  • credentials — a password hash, optionally a passkey and/or an authenticator secret,
  • recovery codes — ten single-use codes, generated at registration,
  • optional linked identities (GitHub).

Usernames are display data. Because they can change, no table stores a username as a foreign key; references always use the user id, and the profile table holds the current username plus a username_history table for cooldowns and anti-impersonation review.

5.2 Registration

  1. Choose username — validated for length (3–24), allowed characters (a-z 0-9 _ -), reserved names, blocked terms, and availability.
  2. Choose password — minimum 12 characters, checked against a breached-password list where available, with no composition rules that push users toward predictable patterns.
  3. Password hashed with a modern memory-hard algorithm (Argon2id with tuned parameters; bcrypt acceptable only if Argon2 is unavailable), never logged, never returned.
  4. Ten recovery codes generated, shown once, stored only as hashes.
  5. Optional: enrol a passkey or authenticator app immediately, with a clear explanation of why it matters when email is absent.

Registration is rate-limited per IP and per fingerprint, and blocked during maintenance mode with an explicit message.

5.3 The reserved Owner account

The username DuckyDrive is reserved and cannot be registered by anyone. The Owner account does not exist by assumption — it is bootstrapped:

  1. A one-time bootstrap secret is generated out of band and stored as a server-side secret (never in the frontend bundle or the repository).
  2. The bootstrap endpoint accepts the secret, the username DuckyDrive, a password, and creates exactly one Owner account, then invalidates the secret.
  3. If an Owner already exists, the endpoint refuses unconditionally.
  4. The Owner receives recovery codes and is required to enrol a second factor.
  5. Every bootstrap attempt is logged with time, result and origin; successful bootstrap triggers an alert.

The Owner cannot be demoted, suspended or removed by other staff. Ownership transfer, if ever needed, is a documented out-of-band procedure, not a UI action.

5.4 Username changes

  • Cooldown of 30 days between changes; the first change is free.
  • Previous usernames are reserved for 180 days to prevent impersonation.
  • Names differing from a staff member's only by lookalike characters (l/1, 0/O) are rejected.
  • Changes are logged and appear in the account's security log.
  • A name change does not break links: profile URLs resolve by id with the username as a slug, and old slugs redirect.

5.5 Sessions, recovery and security

Control Requirement
Session tokens HTTP-only, Secure, SameSite=Lax cookies; short-lived access token with rotating refresh.
Session list Users can see active sessions (device label, last seen, rough location) and revoke any of them.
Password change Requires current password; revokes all other sessions.
Recovery codes Hashed at rest, single-use, regenerating invalidates all previous codes, with a confirmation warning.
Passkeys WebAuthn, at least one registered before the password can be removed from the login path.
2FA TOTP with a manual entry key and QR code; backup via recovery codes.
Rate limits Per-account and per-IP limits on login, recovery and registration; exponential backoff after repeated failures.
CSRF Required on all state-changing requests from cookie sessions using double-submit or same-site origin checks.
Logging Login success/failure, password change, recovery use, factor change, session revocation — visible to the user.

Recovery honesty. Because no email is collected, an account with lost password, lost passkey and lost recovery codes cannot be recovered by automatic means. The interface states this before registration and before a user dismisses their recovery codes. Staff-assisted recovery exists only as a narrow, audited, high-friction process for verified identities, and is not a hidden email mechanism. Owner recovery is a separate documented procedure requiring out-of-band proof.

Avatar and banner uploads are separate from chat: chat accepts no images at all. Uploads are limited to 2 MB, JPEG/PNG/WebP only, re-encoded server-side, stripped of EXIF, served from a controlled bucket with a random object key, and deletable by the owner.

5.7 Privacy controls

A single Settings → Privacy panel controls: profile visibility (public/private), favourite visibility, collection visibility default, online status, activity visibility, activity-based recommendations, notification categories, and blocked users.

Viewer Public profile Private profile
Anyone Username, avatar, join date, public collections, achievements. Username, avatar only.
Friend Adds online status (if enabled), favourites (if enabled), activity feed. Same as friend view of a public profile, minus hidden items.
Staff Moderation-relevant data only, with the access logged. Same.

Private profiles remain discoverable by username but expose no activity. Messages, private collections and reports are never visible to other ordinary users.

5.8 Blocking, deletion and retention

  • Block is unilateral and immediate: it hides both profiles from each other, ends any friendship, blocks new friend requests and messages, and hides comment replies between them. Blocks are not announced to the blocked user.
  • Account deletion is requestable from Settings with password re-entry plus a second factor or recovery code. A 14-day grace period allows cancellation.
  • On deletion, personal data is removed or anonymised: profile, uploads, private collections, messages authored in DMs, friend relationships, notification history. Content that forms part of public record (public comments, ratings, public collection metadata) is retained but attributed to a deleted-user placeholder, or removed where the user requested removal and no safety obligation applies.
  • Moderation, audit and security records are retained for a defined period (Chapter 13) independent of account deletion, with access restricted to staff.
  • Deletion is logged; the log records the request, the grace period and the completion, not the deleted content.
