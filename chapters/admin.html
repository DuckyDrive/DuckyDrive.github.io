Chapter 12 · Sections 29-31

Admin Panel, Staff Roles & Moderation

Deny by default. Three staff tiers. No Developer role. Every privileged action is checked server-side and logged.

12.1 Hierarchy

Tier Granted by Scope
Owner Bootstrap only Full control. Cannot be demoted, suspended or removed by any other staff member.
Administrator Owner Only the permissions explicitly granted. A new Administrator starts with none until a preset or custom set is applied.
Moderator Owner Community moderation only: chat, comments, reports, conduct. No platform configuration, staff management, GitHub integration, deployment or DLES powers unless separately granted.

There is no general Developer role. Game creation and editing belongs to the Owner and verified GitHub contributors of that repository — an Administrator without repository access cannot edit a game.

12.2 Permission model

Permissions are named capabilities, granted individually, evaluated server-side on every request.

Suggested presets (templates, not immutable roles): Full Administrator, Community Administrator, Game/Project Catalogue Administrator, Chat Moderator, Custom.

Permission Grants Typical holder
reports.view / reports.resolve Read and resolve the moderation queue Moderator
chat.remove / chat.mute Remove messages, temporarily mute Moderator
comments.moderate Remove or restore comments Moderator
users.warn / users.suspend / users.ban Enforcement actions Moderator (warn/suspend), Admin (ban)
appeals.review Decide appeals Admin
catalogue.manage Edit, hide, unlist, recategorise projects Admin
catalogue.feature Feature/unfeature on the homepage Admin
announcements.manage Global announcements Admin
dles.* Live event operations (see Chapter 11) Admin
settings.manage Platform settings, maintenance mode Admin
github.manage GitHub integration state Admin + Owner approval
deployments.manage Trigger or retry deployments Admin, only where explicitly granted
staff.manage Appoint/remove staff, change permissions Owner only by default
recovery.assist Staff-assisted account recovery Owner only
audit.view Read audit logs Admin

Rules:

  • Deny by default: absence of a grant means refusal, and the API returns a structured permission_denied naming the required capability.
  • Role labels never imply permissions; only grants do.
  • No self-escalation: a user cannot grant themselves a permission, and an Administrator cannot create another Administrator.
  • Owner-only actions return 409 target_is_owner when aimed at the Owner, and 403 when performed by a non-Owner.
  • Permission changes take effect on the next request, not the next login, because permissions are read from the database per action.

12.3 Admin Panel modules

  • Users — search, profile view, enforcement history, sessions, delete/anonymise requests.
  • Staff — grants, presets, audit of every change (Owner only).
  • Reports — queue with priority, target snapshot, one-click actions, notes.
  • Enforcement — warnings, mutes, suspensions, bans, appeals.
  • Catalogue — project list, validation errors, hide/unlist, recategorise, feature, merge duplicates.
  • GitHub — repository sync state, webhook health, failed validations, stale scans.
  • Deployments — status per project, logs, retry, rollback.
  • DLES — event control per Chapter 11.
  • Announcements — global banner and inbox messages.
  • Settings — feature flags, rate limits, maintenance mode.
  • Audit log — filterable by actor, action, target, time.
  • Health — dependency status (database, storage, realtime, GitHub), error rate, queue depth.

There is no build studio, no per-game analytics dashboard, and no code editor in the Admin Panel.

12.4 Moderation workflow

Report categories: harassment, hate, spam, impersonation, sexual content, violence, self-harm, illegal content, cheat/malware distribution, stolen work, other.

Flow:

  1. Report submitted with category, optional note, and an automatic snapshot of the target content.
  2. Duplicate reports on the same target and category within 24 hours merge into one thread, incrementing a counter that raises priority.
  3. Queue ordered by severity, report count, and target risk; automated triage flags obvious spam and new-account brigading.
  4. A moderator claims a report, which locks it for a short window to avoid double handling.
  5. Action: dismiss with reason, warn, mute, remove content, suspend (temporary), ban (permanent). Every action requires a reason code; free-text notes are optional.
  6. The target is notified where policy allows, with the reason category and appeal path. Reporters are told the report was handled, not who did what.
  7. Appeals are filed within 30 days, reviewed by a different staff member where one is available; the decision and reasoning are recorded.
  8. Every step is an audit entry: actor, target, action, reason, timestamp, related report id.

12.5 Enforcement effects on other systems

Enforcement Effect
Warning Recorded; may restrict posting after repeats.
Mute Chat/comment posting blocked until expiry; reading continues.
Suspension Login allowed for appeal and settings only; no posting, no XP earned, removed from leaderboards at next snapshot, ratings excluded from aggregates.
Ban Sessions revoked; content hidden pending review; no XP; excluded from all boards and public counts.
Owner action Same as above, but cannot target the Owner and requires a second confirmation.

Lifting enforcement restores participation immediately and restores aggregates at the next recalculation, with an audit record of the change.

12.6 Staff safety

  • All staff require a second factor; the Owner requires a passkey.
  • Staff sessions expire faster (12 hours) than member sessions.
  • Every privileged endpoint validates: authenticated session, non-revoked, permission grant present, target not protected, request same-origin, and a rate limit.
  • Sensitive actions (bans, deletions, permission changes) require a confirmation dialog stating the exact consequence.
  • Removing a staff member revokes their grants and sessions; the audit entry names the remover.
  • If a staff account is suspended or deleted, its grants are removed and its in-flight privileged sessions are revoked.
  • Access to private data is itself logged, including moderator reads of reported conversations.

12.7 Audit log requirements

Append-only, written by the server, never editable from the UI. Each row: actor_id, action, target_type, target_id, reason_code, metadata (previous and new values where relevant), ip_hash, created_at. Retention per Chapter 13. Audit rows survive account deletion with the actor replaced by an immutable id, so history cannot be rewritten by deleting an account.
