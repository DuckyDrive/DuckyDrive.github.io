Executive Summary & Vision

DuckyDrive is a gaming and project-discovery platform with one central application, a catalogue of games and projects, a username-only identity system, and a GitHub-powered publishing pipeline.

1.1 What DuckyDrive is

DuckyDrive is a place to find, play and follow games, websites, software experiments and source repositories. It combines four things that are usually separate products:

  1. A discovery catalogue — browse, search, filter and get recommended projects.
  2. A launch surface — games live in their own repositories and open full-screen from the catalogue.
  3. A community layer — accounts, profiles, friends, public chat, private messages, ratings, comments, collections and leaderboards.
  4. A publishing pipeline — GitHub is the source of truth for project source, releases and deployment, and discovery is largely automatic.

The platform is deliberately not a generic file listing and not a clone of an existing game portal. Its identity comes from the combination of automatic GitHub discovery, first-class game hosting on one domain, and a social layer that is quiet by design.

1.2 Who it serves

Audience What they need from DuckyDrive
Players Find something good quickly, launch it in one click, track what they played and what they want to play.
Creators and contributors A place to publish a project that updates itself from GitHub, without maintaining a separate site and catalogue entry.
The Owner and staff A single Admin Panel for catalogue curation, moderation, announcements and live events.
Connected GitHub accounts Consent-based discovery of their public, validated projects, with editing rights tied to real repository permissions.

1.3 The one-application rule

This is the structural decision that governs every other decision in this document.

Home, Games, Sites, Repositories, Software, Experiments, Newly Added, Recently Updated, Trending, Featured, Following, Chat, Library, Settings and the Admin Panel are views inside one application shell. They share one design system, one session, one router and one backend.

Games are the deliberate exception, and only because they are separate codebases: each game is its own repository deployed to its own path (https://duckydrive.github.io/game-one/) and opens full-screen. There is no embedded player by default.

The consequence is that "splitting Games into its own site" or "giving Chat its own domain" is never a valid implementation shortcut. If a section grows large, it is lazily loaded as a route inside the same shell.

1.4 Product principles

Principle What it means in practice
One shell, many views Every catalogue and social section shares the sidebar, search, session and design tokens.
GitHub is the source of truth Source, releases, versions and deployment state come from GitHub. DuckyDrive never becomes a second place to edit code.
Automatic but gated New projects publish automatically after validation passes. Automatic publishing is not automatic code execution.
Untrusted by default Repository content, client input, chat text and game clients are all untrusted until validated server-side.
Quiet social Following is silent. Notifications exist for the things a person asked for. No engagement farming.
Deny by default Every privileged action is checked server-side against an explicit permission, never inferred from a role label.
Privacy by minimisation No mandatory email. Activity-based personalisation can be switched off. No private analytics dashboard.
Accessible by construction Keyboard navigation, visible focus, contrast and reduced motion are requirements, not polish.

1.5 Goals and success criteria

DuckyDrive succeeds when:

  • A new player can reach a game and be playing it within three interactions from the landing page.
  • A creator can push a release to GitHub and see the catalogue entry update without touching DuckyDrive.
  • A contributor can edit only the games they actually have GitHub access to, verified server-side.
  • A moderator can resolve a report, and the action is attributable in the audit log.
  • The catalogue stays clean: no private, unfinished or malformed projects appear publicly.
  • The platform remains usable on a mid-range phone over a slow connection.

1.6 Scope of this document

In scope: product requirements, information architecture, UI/UX system, data model, API contracts, security model, permissions, deployment, testing, operations and roadmap, with pseudocode, SQL-like schema definitions, JSON examples and diagrams where they clarify intent.

Out of scope, by instruction:

  • Writing application code or generating a starter project.
  • Creating repositories, Supabase projects or GitHub applications.
  • Deploying anything or configuring providers.
  • Claiming a prototype has validated an assumption before it has been built.

Anything that needs proof is recorded in the validation register in Open Questions, Glossary & Appendices rather than presented as settled.

1.7 How to read this specification

The chapters follow the required output structure. They are ordered for implementation: vision and decisions first, then design, then product areas, then the backend, then operations and delivery. Cross-references point at the chapter that owns a topic rather than repeating rules, so a rule such as "following never notifies" appears once as a decision and is referenced everywhere it applies.

This document is a plan. No application code has been written, no repository has been created for the platform itself, and no provider has been configured. The site you are reading is the specification, not the product.
