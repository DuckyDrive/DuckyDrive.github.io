Chapter 16 · Sections 42-44

Roadmap, Acceptance Criteria & Risk

Eleven phases, each with an exit condition. Nothing starts before its prerequisites are met.

16.1 Minimum viable product

The MVP is the smallest version that is genuinely useful without compromising the architecture: a unified shell with catalogue browsing, project detail pages, GitHub discovery with validation, game launching from separate deployments, accounts with favourites and follows, and ratings and comments. Chat, DLES, XP and the Admin Panel follow — the data model already accounts for them, so they are additions rather than redesigns.

16.2 Phases

Phase 0 — Requirements validation

Objectives: confirm the six assumptions in Chapter 2. Deliverables: a de-risking prototype for username-only auth, a Pages prototype for main app plus one game path, a GitHub App permission probe, a free-tier limit measurement. Exit: every assumption marked validated or the fallback chosen. Risk: provider limits appear only at scale — measure deliberately. Do not start: any product UI.

Phase 1 — Foundations

Objectives: repository structure, design system implementation, application shell, CI/CD. Features: routing, sidebar/rail/drawer nav, search affordance, theme tokens, component library, build and deploy pipeline, staging environment. Dependencies: Phase 0. Exit: shell deploys to staging, passes accessibility smoke test, and a game repository deploys to its own path without collision.

Phase 2 — Identity and members

Objectives: DuckyDrive ID, profiles, permissions skeleton. Features: registration, login, recovery codes, sessions, passkeys/2FA, profile editing, avatar/banner upload with moderation hooks, privacy settings, Owner bootstrap. Dependencies: Phase 1. Exit: a member can register, log in on two devices, revoke a session, and recover an account with a recovery code; a non-owner cannot take the reserved username.

Phase 3 — Catalogue and discovery

Objectives: projects, categories, tags, search, automatic GitHub discovery and validation. Features: catalogue surfaces, project pages, filters and sorts, duckydrive.json validation, webhook receiver, daily reconciliation, automatic publishing, hide/unlist controls. Dependencies: Phases 1–2. Exit: 20 real repositories discovered, 5 deliberately broken ones withheld with recorded reasons, and no private repository listed.

Phase 4 — Launch, library and feedback

Objectives: play sessions, update history, favourites, follows, collections, ratings, comments. Features: Play action, release history from GitHub Releases, follows, favourites, saved, recently played, collections (public/private/follow/like), ratings with weighting, comments with replies and reports. Dependencies: Phase 3. Exit: a new release updates the project page within a minute of the webhook; a rating edit recalculates the average; duplicate collection items are impossible.

Phase 5 — Social

Objectives: friends, chat, DMs, notifications. Features: friend requests, blocks, public rooms with moderation, friend-only DMs, reactions, notifications with categories, quiet hours. Dependencies: Phase 2. Exit: presence is off by default, chat rejects all attachments, and following a project produces no notification.

Phase 6 — Progression

Objectives: XP, achievements, leaderboards, recommendations, trending. Features: achievement families and tiers, XP ledger with caps, global/weekly/monthly boards, contributor ranking, trending computation with anti-abuse, recommendation controls. Dependencies: Phases 3–4. Exit: duplicated XP awards are rejected by the database, and a disabled recommendation setting produces a non-personalised feed.

Phase 7 — Administration

Objectives: Admin Panel, moderation, appeals, audit. Features: reports queue, enforcement actions, appeals, catalogue management, feature/unlist, announcements, settings, audit viewer, health view. Dependencies: Phases 2–4. Exit: every action in the required negative test list returns the specified refusal and writes an audit row.

Phase 8 — SDK

Objectives: game integration path. Features: SDK package, handshake, session reporting, capability declaration, first supported game integrating it end to end. Dependencies: Phase 4. Exit: a game reports sessions, plays appear in statistics once per session, and a forged reward request is rejected.

Phase 9 — DLES

Objectives: global live events. Features: coordinator, capability gating, announcements, audio, visual effects, spawning, rewards, temporary controls, emergency stop, dashboard, audit. Dependencies: Phase 8. Exit: a two-server test game receives a global announcement, survives a server restart mid-event, restores state on stop, and cannot be started twice.

Phase 10 — Hardening and launch

Objectives: performance, accessibility, backups, abuse resistance, public launch. Features: load test, accessibility audit, restore drill, rate-limit tuning, documentation, launch checklist. Dependencies: all prior phases for the surfaces being launched. Exit: budgets met on a mid-range phone, restore drill passed, no open critical risk.

16.3 Feature acceptance criteria

Feature Criterion
Catalogue list Anonymous request returns only publicly visible, validated projects, paginated at 24, in the requested sort.
Project page Shows hosting badge, latest version, update history and stats; unverified fields labelled, not guessed.
Play Opens the game's own path full-screen; a project whose deployment is not confirmed shows no Play action.
Search Two-character minimum, debounced, grouped suggestions, filtered server-side, rate limited.
Trending Recomputed hourly from the weighted formula; refresh spam cannot raise a project's score.
Newly added Orders by discovery date, unaffected by repository creation date.
Follow Idempotent, updates follower count, produces no notification.
Collections Owner-only writes, duplicates rejected, public/private respected after toggling.
Ratings One per account, editable, aggregates recalculated, moderated aggregates audited.
Comments Two levels, likes, reports, creator reply marked, tombstones after removal.
Chat Text/reactions only, rate limited, moderated, realtime with polling fallback.
DMs Friend-only, no attachments, unsend window, report snapshots.
Notifications Category-controlled, deduplicated by event key, security alerts always on.
Achievements Granted once, XP ledger append-only, daily caps enforced.
GitHub discovery Signed webhooks, idempotent processing, 24-hour reconciliation, stale sync flagged.
Publishing Publishes on validation pass; withholds on any error code; restores when valid again.
duckydrive.json Minimal file publishes; every documented error code blocks; unknown fields preserved.
Deployments Atomic, path-scoped, absolute-path references rejected, smoke test before "live".
Owner bootstrap One-time secret, single Owner, refused when one exists, every attempt logged.
Permissions Deny by default, per-request checks, Owner protected, staff changes audited.
DLES Manual start/stop, capability-gated, idempotent actions, global emergency stop.

16.4 Risk register

Risk Likelihood Impact Mitigation
Provider forces email-based auth Medium High Auth adapter prototype in Phase 0; fallback to a session service.
Free-tier limits reached early Medium Medium Measure in Phase 0; cache aggressively; document the upgrade point.
Pages limits block frequent game deploys Low Medium Reusable workflow, atomic folder deploys, monitor build minutes.
Metadata quality is poor across projects High Medium Minimal valid file, tolerant warnings, staff correction tools.
Trending manipulated Medium Medium Time weighting, dedupe, new-account weighting, audit of anomalies.
Scope creep toward a game portal clone Medium High Chapter 2 non-goals are enforced in review.
Chat abuse at launch Medium Medium Slow mode, rate limits, more moderators than rooms.
Game deployments collide Low High Slug reservation, path validation, absolute-path rejection.
Secret leakage Low High Server-only secrets, scanning, rotation runbook.
Accessibility regressions Medium Medium Automated axe in CI plus manual passes per phase.
Backup untested Medium High Quarterly restore drill with verified counts.

16.5 What must not start early

  • Chat before moderation tooling exists (Phase 7 pieces are pulled forward into Phase 5 for chat-specific actions).
  • DLES before capability manifests and the SDK handshake are proven (Phase 8 before Phase 9).
  • Leaderboards before the XP ledger is append-only and capped.
  • Any per-game deployment before slug reservation and path validation exist.
