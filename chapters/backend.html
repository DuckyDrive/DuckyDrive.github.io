Supabase, Database & Service Contracts

Supabase is the planned backend, subject to prototype validation. The frontend is public, so every sensitive rule is enforced server-side.

10.1 Architecture

GitHub Pages (public SPA)
   │  anon key, RLS-scoped reads
   ├──────────────► Supabase Postgres + RLS
   │                     ▲
   │                     │ service role (server only)
   └──► Edge Functions ──┘
          ├── auth adapter (username-only credentials)
          ├── GitHub webhook receiver
          ├── repository scan + validation jobs
          ├── XP / achievement awards
          ├── DLES coordinator
          └── moderation + admin actions

Constraints:

  • The service-role key exists only in Edge Function secrets. It is never bundled, never in the repository, never in a public variable.
  • The browser holds the anon key and can only do what RLS permits.
  • Every privileged operation is an Edge Function that authenticates the caller, re-checks permissions against the database, then acts.
  • Client-supplied user ids, roles, XP totals, permissions and reward claims are ignored; the server derives them.
  • Environment separation: dev, staging, prod projects with separate keys and separate data. No cross-environment references.

10.2 Identity on Supabase

The provider's built-in email-based auth cannot be used as-is because no email is collected. The planned adapter:

  1. A credentials table holds username → password hash, passkey records and TOTP secrets, managed only by Edge Functions.
  2. Successful credential verification issues a short-lived session token (signed JWT with sub = user_id), rotated on refresh.
  3. Postgres RLS reads the verified sub claim; it never trusts a client-provided id.
  4. Validation task: confirm the adapter's security properties (session revocation, replay resistance, cookie handling with a static frontend) before commitment. Fallback: self-hosted session service with Supabase used only for database, storage and realtime.

10.3 Proposed schema (core tables)

All tables use uuid primary keys (gen_random_uuid()), created_at/updated_at timestamps, and never expose a raw username as a foreign key.

10.4 Database rules

  • Referential integrity: real foreign keys everywhere, on delete cascade for dependent rows (collection items, likes), on delete set null for authors of retained public content, restrict where deletion would orphan moderation records.
  • Soft deletion: deleted_at on user-authored public content (comments, collections) so tombstones and appeals work; hard deletion for private data on removal.
  • Counters: project_stats is the single source for public counts, updated in the same transaction as the action, with a nightly reconciliation from base tables.
  • Idempotency: unique constraints are the mechanism — favourites, follows, ratings, likes, achievement grants, XP awards, DLES rewards all have explicit uniques.
  • Username changes: nothing references usernames; all FKs use ids.
  • Search: a materialised project_search document refreshed on project change, with a Postgres full-text index.
  • Migrations: versioned SQL files, forward-only, applied through CI; each has a documented rollback (compensating migration), never an ad-hoc edit in production.

10.5 Service contracts

Format: METHOD /path with auth class, inputs, outputs, errors, limits.

GET /projects?type=game&category=rhythm&sort=trending&page=1
Auth: public
200 { items: [{ id, slug, name, description, thumbnail, types, hostingStatus, rating: {avg,count}, followers }],
      page: 1, total: 128 }
429 { error: "rate_limited", retryAfterMs: 1200 }

POST /projects/{id}/ratings
Auth: member
Body: { score: 1..5 }
200  { score, average, count }
409  { error: "duplicate_rating", hint: "PATCH to update" }
403  { error: "enforcement_active" }

POST /collections/{id}/items
Auth: collection owner
Body: { projectId }
201  { collectionId, projectId, position }
409  { error: "already_in_collection" }
422  { error: "validation_failed", fields: { projectId: "not_visible" } }

POST /github/webhook
Auth: HMAC signature
Headers: X-Hub-Signature-256, X-GitHub-Delivery, X-GitHub-Event
202  { queued: true }
401  { error: "bad_signature" }   // logged, never retried by GitHub

POST /admin/users/{id}/suspend
Auth: staff with `moderate.suspend`
Body: { reasonCode, note, durationHours }
200  { suspensionId, expiresAt }
403  { error: "permission_denied", required: "moderate.suspend" }
409  { error: "target_is_owner" }

POST /dles/events/{id}/actions
Auth: staff with `dles.operate`; game-server acknowledgement endpoint uses scoped game credentials
Body: { capability: "announcement", payload: { text, style, durationSeconds } }
202  { actionId, queued: true }
422  { error: "capability_not_declared" }

Every endpoint documents: auth class (public, member, contributor, staff, owner, game-server), authorisation rule, validation, error codes, rate limit, idempotency key behaviour and audit requirement. Contracts are examples of shape and are not live service definitions.

10.6 Rate limiting and abuse controls

Token buckets per account and per IP at the edge function layer, with per-route budgets: auth 10/min, writes 30/min, search 60/min, reports 5/hour, DLES actions 20/min with high-impact actions requiring confirmation. Exceeding a bucket returns 429 with a retry hint; repeated abuse escalates to a temporary block and produces an audit entry.
