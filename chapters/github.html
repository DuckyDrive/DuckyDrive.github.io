GitHub Integration, Deployments & Auto-Publishing

GitHub is the source of truth. Discovery is automatic, publishing is automatic after validation, and validation never executes repository code.

8.1 Sources of discovery

Two sources, one pipeline:

  1. Repositories in the DuckyDrive GitHub organisation/account.
  2. Repositories of GitHub accounts explicitly connected by contributors, limited to the scope the contributor selected.

A GitHub username typed into a profile is never treated as identity proof. Connected-account consent is explicit, minimal-scope, and revocable at any time with an immediate effect on discovery and editing rights.

8.2 Events and schedule

Trigger Purpose
repository events Creation, deletion, rename, transfer, visibility change.
release events Published, edited, deleted, prerelease flag changes.
push events Detect meaningful update activity when no release exists.
Daily reconciliation scan Recover from missed webhooks, detect drift, verify access.
Manual resync Staff or owner action for a specific project.

Webhook handling rules:

  • Verify the signature on the raw body before parsing.
  • Persist the event with its delivery id and make processing idempotent on that id.
  • Process asynchronously, with retries and a dead-letter record after repeated failure.
  • Handle out-of-order delivery by comparing event timestamps against the stored sync state rather than assuming arrival order.
  • Treat duplicate deliveries as no-ops.
  • Record last_successful_scan per repository and surface stale sync in the Admin Panel.

8.3 What is inspected

duckydrive.json (preferred), README, GitHub topics, package.json, HTML metadata, build configuration, GitHub Pages configuration, release metadata, repository visibility and access permissions.

Signals are weighted, not blindly trusted. Conflicts resolve to the most specific source: metadata file, then release, then topics, then README heuristics — and a conflict that cannot be resolved leaves the field unset rather than guessed.

Security: repository content is untrusted input. Discovery parses data; it never executes repository scripts, never evaluates expressions from the repo, and never runs a build during discovery. Builds happen only in controlled CI with isolated permissions.

8.4 Validation gate

A discovered project becomes public only when all checks pass:

Check Failure behaviour
Repository is public (or explicitly published by an authorised owner) Withheld.
duckydrive.json parses against the schema (or is absent and minimal metadata is derivable) Withheld with a validation error recorded.
Required fields present: name, description, type Withheld.
Project type recognised and not contradictory Left uncategorised.
Project is not obviously unfinished (empty repo, template placeholder, no entry point for a game) Withheld.
URLs are safe: same-origin paths or https, no javascript:, no data URLs Withheld.
Thumbnail and screenshots resolve to allowed hosts and formats Field dropped, project may still publish.
No duplicate identity (same repository already mapped to another project) Merged or flagged, not duplicated.
Repository still accessible to the scanner Withheld and marked access_lost.

Failures are recorded per check with a machine code and a human sentence, visible in the Admin Panel. There is no default manual approval queue — passing projects publish automatically.

8.5 Losing validity later

When a published project later fails validation (repository made private, deleted, renamed without redirect, deployment broken, metadata corrupted):

  1. Set visibility = withheld and keep the record for audit and restoration.
  2. Remove it from all public catalogue surfaces, search and trending within one catalogue refresh.
  3. Preserve favourites, ratings and stats but do not display the project page publicly.
  4. Show the owner a clear reason in their own project view.
  5. Restore automatically when validation passes again, with the original discovery date kept.

8.6 Game deployment model

Every game is its own repository. Each deploys to its own folder on the same domain:

https://duckydrive.github.io/            main application (this repository)
https://duckydrive.github.io/game-one/   game one deployment
https://duckydrive.github.io/game-two/   game two deployment

Rules that prevent collisions:

  • Each game workflow publishes only to /<its-declared-slug>/ and never to /.
  • The slug is declared in duckydrive.json and reserved in the platform database; duplicates are rejected at validation.
  • Assets must be referenced relative (./assets/...) or with the declared base path. Absolute /assets/... references are a validation error for game builds because they resolve to the main application's files.
  • SPA fallback is per-folder: a game that needs routing ships its own 404.html or uses hash routing. The main application must not own a catch-all that swallows game routes.
  • Deployments are atomic: upload to a staging path or commit to a gh-pages branch that only serves that folder, so a failed build never leaves a half-published game.
  • The catalogue marks a deployment live only after GitHub Pages reports a completed build and a smoke fetch of /<slug>/ returns 200 with the expected entry document.
  • Versioned assets are cached long; the entry HTML is cached short. A new release invalidates through the HTML reference, not through a cache purge API.

The main repository and each game run the same required checks: metadata validation, build, output path validation, forbidden-absolute-path scan, and a post-deploy smoke test.

8.7 Releases and update history

  • GitHub Releases are the primary source of version, date and notes.
  • Commit history is a fallback only when a project has no releases, and the UI labels it accordingly ("No releases published; showing recent commits").
  • Drafts are ignored. Prereleases are stored and shown with a prerelease badge but do not become "latest stable".
  • Deleting a release removes it from update history and recomputes the latest version; the deletion is audited.
  • Failed deployments do not produce a public update entry: a release is recorded as public only when its deployment, if any, is confirmed.
  • Every game page shows an Update History section, newest first, with the latest entry highlighted.

8.8 Permissions model for editing

Capability Required proof
Discover a repository Public repository, or contributor consent for that repository.
Edit project metadata Owner, or verified GitHub repository permission (admin/maintain/push) checked server-side at action time.
Trigger deployment Same as edit, plus deployment permission explicitly granted.
Hide/feature a project Staff catalogue permission.
Manage GitHub integration for the org Staff permission + Owner approval.

Admin status alone never grants game editing. Permission is re-checked on every privileged action rather than cached in a session claim, so revocation on GitHub takes effect at the next action. Revoking GitHub access removes editing permission immediately; the project remains published, attributed to the repository's current collaborators.

8.9 Rate limits and resilience

  • GitHub API calls are made with a token pool, conditional requests (ETag), and a per-installation budget.
  • On rate-limit response, jobs are deferred with backoff; the daily scan resumes from the last successful cursor.
  • Webhook bursts are queued with per-repository ordering.
  • If GitHub is unreachable, the catalogue serves cached data, labels the data as possibly stale, and the Admin Panel shows integration health.
