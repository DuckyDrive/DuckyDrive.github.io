Chapter 02 · Sections 4-5

Confirmed Decisions & Non-Goals

The locked decisions, the defaults chosen to keep delivery fast, and the features that must not appear.

2.1 Locked decisions

These are confirmed product decisions. Where a later chapter appears to conflict with one of them, the decision wins and the chapter is corrected.

# Decision Enforcement point
D1 One unified main application; sections are internal views. Router and build layout; no per-section deployment.
D2 Games are separate repositories deployed to separate paths on the same domain, opened full-screen. Deployment pipeline; project launch action.
D3 Username + password accounts with no mandatory email. Registration and recovery flows.
D4 Recovery codes are the primary recovery mechanism; passkeys and authenticator 2FA are optional. Identity service.
D5 The username DuckyDrive is reserved for the Owner and cannot be registered by anyone else. Username uniqueness check and registration.
D6 There is no general Developer staff role. Permission model — the role does not exist.
D7 Game editing requires verified GitHub repository permission. Admin status alone does not grant it. GitHub permission check on every edit action.
D8 No image, video or file attachments in public chat or private messages, and no external-URL workaround. Message schema and validation.
D9 Following a project never generates an update notification. Notification rules.
D10 No seasonal competitions, seasonal leaderboard resets or exclusive seasonal badges. XP and leaderboard module.
D11 DLES live events are scheduled manually by authorised staff; no automatic or recurring event starts. Event coordinator.
D12 No private developer analytics dashboard; public statistics only. Product surface inventory.
D13 Newly discovered, valid projects publish automatically after validation; there is no default manual approval queue. Discovery pipeline.
D14 Staff hierarchy is Owner → Administrator → Moderator only. Permission model.
D15 Announcements in games appear as a top-of-screen banner, never a centre-screen takeover. DLES announcement capability.
D16 The Admin Panel is platform administration, not a developer studio. Admin module list.

2.2 Explicit non-goals

The following must not be built, even as a "small" addition, because each one contradicts a confirmed decision or expands scope without need:

  • A second Developer dashboard for game analytics, build logs or player funnels.
  • Chat or DM attachments of any kind, including embeds that reference external images as a workaround.
  • Project-update notifications triggered by following.
  • Seasonal events, seasonal resets, or badges that expire with a season.
  • Automatic recurring DLES schedules or cron-driven event starts.
  • Separate hosted applications for Chat, Library, Settings or Admin.
  • A generic Developer staff role that grants game edit rights.
  • Email collection as a required account field, or a hidden email-based recovery path.
  • An embedded game player as the default launch behaviour.
  • Per-project discussion forums; comments and replies cover this need.
  • Auto-deployment of private, unfinished, unsupported or unvalidated projects.

2.3 Recommended defaults

These are chosen for speed and are reversible. They are documented so implementation does not stall on small questions.

Area Default Revisit when
Backend Supabase (Postgres, Auth-compatible identity, RLS, Storage, Realtime, Edge Functions) Prototype shows username-only auth or free-tier limits are unworkable.
Frontend hosting GitHub Pages Pages limits (build size, no server runtime) block a required feature.
Frontend stack One static SPA shell with route-level code splitting SEO demands per-route pre-rendering.
Release source GitHub Releases; commit history only as a documented fallback A project has no releases at all.
Trending window 14-day weighted activity Data shows the window is too short or too long.
Rating scale 1–5 stars, one per account per project, editable Product decision to change scale.
Comment depth Two levels (comment, reply) Threading is genuinely required.
Discovery scan Webhook-driven with a 24-hour reconciliation scan Webhook volume or rate limits require change.
Progression caps Daily XP caps per activity family Abuse data shows caps are wrong.

2.4 Assumptions to validate before commitment

  1. Username-only authentication can be implemented securely on the chosen provider without a mandatory email identifier. If the provider forces email, identity moves behind a server-side credential service and the provider becomes storage + database only.
  2. Free-tier limits (database size, storage, realtime connections, edge function invocations, inactivity pausing) are sufficient for a prototype and early launch.
  3. GitHub Pages can host the main application and many game deployments with per-path isolation, without a build step that exceeds Pages limits.
  4. GitHub App permissions allow read-only discovery plus server-side permission checks for contributors, without asking every user for broad write scopes.
  5. Webhook delivery is reliable enough for near-real-time updates, with the daily scan as the safety net.
  6. Realtime chat stays within connection and message quotas at expected concurrency.

Each assumption is tracked in the validation register (Chapter 17) with an owner-facing decision and a fallback.

2.5 Consistency review rule

Before any chapter is considered final, it is checked against the table in 2.1. The check is mechanical: for each decision, point at the code path or interface that enforces it. A decision with no enforcement point is not a decision, it is a wish.

Nothing in this chapter authorises implementation. It records what has already been agreed so the build does not reopen it.
