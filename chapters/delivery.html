Chapter 15 · Sections 38-41

CI/CD, Freebuff Workflow & Operations

GitHub is the pipeline. Freebuff is the authoring environment. Nothing is published without review and a green build.

15.1 Repositories and naming

Repository Purpose Pages target
DuckyDrive/DuckyDrive.github.io Main application https://duckydrive.github.io/
DuckyDrive/<game-slug> One repository per game https://duckydrive.github.io/<game-slug>/
DuckyDrive/spec (optional) This specification site separate path or project site

Naming: lowercase, hyphenated, matching the declared slug exactly. The slug is reserved in the database before the repository is created, so two games cannot claim the same path.

15.2 Branching and review

  • main is protected: no direct pushes for anyone except the Owner's documented emergency procedure.
  • Work happens on short-lived branches (feat/catalogue-filters, fix/chat-reconnect).
  • Every change opens a pull request with a description of intent and risk.
  • Required checks must pass: typecheck, lint, unit and integration tests, metadata validation (for game repos), build, output-path validation, accessibility smoke test (main app).
  • At least one approval is required. The Owner can merge their own changes, but the checks still apply.
  • Squash merge keeps history readable; the PR title becomes the commit subject.
  • Release tags are vMAJOR.MINOR.PATCH and are created only from main.

15.3 Deployment strategy

Main application:

  1. CI builds the SPA for the GitHub Pages base path (/<repo>/ or /).
  2. It validates that no asset references an absolute root path that would break a project-site deployment.
  3. It publishes atomically to Pages.
  4. A post-deploy smoke test fetches the landing page, a project page, the manifest and the API health endpoint, and fails the workflow if any is not 200 with expected content.

Game repositories follow the same shape with their own folder as the target. A reusable workflow holds the shared steps so games do not each reinvent them.

Staging: a separate Pages environment (or a project page under a staging repository) built from main before production promotion, with a staging Supabase project. Secrets are per-environment and never shared.

Rollback: redeploy the previous known-good commit (Pages keeps the artifact history), or revert the merge commit and re-run the pipeline. Database changes roll back by applying the compensating migration, never by restoring a production snapshot over live data.

15.4 Environment variables and secrets

Where Contains
Build-time public variables API base URL, Supabase URL, anon key, feature flags safe for public use.
Frontend bundle Nothing else. Ever.
CI secrets Deployment token, Pages token, secret-scanning notification webhook.
Edge function secrets Service-role key, GitHub App private key, webhook signing secret, signing keys.

Secret handling rules: no secret in a public repository, no secret in a client bundle, rotation runbook for every key, secret scanning enabled, and CI failing the build if a high-entropy string appears in a public artifact.

15.5 Database migrations

  • SQL migrations live in version control, numbered and forward-only.
  • Applied by CI to staging, verified, then to production on merge.
  • Each migration states its rollback (a compensating migration) and its data impact.
  • Destructive changes are two-step: add the new column, backfill, switch reads, then remove the old column in a later release.
  • Migration failures halt the pipeline; no partial application.
  • Schema changes that affect RLS ship with the matching policy tests.

15.6 Freebuff workflow

Freebuff is the authoring environment for this project, not a replacement for review.

Expected behaviour:

  1. Read the specification (this site) before making product decisions.
  2. Work inside the relevant repository and follow its instructions.
  3. Generate and maintain duckydrive.json for any new game, including in a new chat, filling only known fields.
  4. Add the SDK or DLES integration only when asked, and only within declared capabilities.
  5. Run the project's checks and report what passed and what did not.
  6. Explain changed files and risks in plain language.
  7. Never publish or deploy without the agreed review and approval flow.
  8. Keep diffs reviewable, preserve existing code, avoid destructive rewrites.
  9. If the project is clearly unrelated to DuckyDrive, do not add DuckyDrive metadata.

Persistent rule: the duckydrive.json requirement is a standing workflow instruction, not something the user must repeat per project.

15.7 Release checklist

  • All required checks green on main
  • Migration applied to staging and verified
  • Feature flags set for the intended rollout
  • duckydrive.json validated for every changed game
  • Deployment output paths verified against collisions
  • Accessibility smoke test passed
  • Rollback plan identified
  • Post-deploy smoke test passed
  • Release notes written for user-visible changes

15.8 Monitoring and observability

Signal Source Alert threshold
Error rate Edge function logs > 2% of requests over 5 min
Auth failures Auth adapter > 20 failed logins/min from one origin
Deployment failures CI + Pages status any failure on main
Webhook backlog Queue depth > 100 pending or oldest > 10 min
Sync staleness last_successful_scan > 30 h for any active repository
Realtime disconnects Channel metrics > 10% of sessions in 10 min
Database saturation Provider metrics connection or CPU > 80%
Abuse signals Rate-limit hits, report spike 3× baseline in an hour

Dashboards are operational only and staff-facing. There is no developer-facing analytics product.

15.9 Backup and disaster recovery

  • Database: daily automatic backups plus point-in-time recovery where the plan allows; a weekly verified restore into a scratch project.
  • Storage: profile artwork backed up on the same schedule; assets are re-derivable from source if lost.
  • Source: GitHub is the backup for code; local and CI clones are disposable.
  • Configuration: secrets in a documented secret store with recovery access for the Owner only.
  • RPO/RTO targets: RPO 24 h (1 h with PITR), RTO 4 h for a full restore at prototype scale.
  • Free-tier honesty: automatic backups and retention differ by plan; if the plan does not provide PITR or long retention, the specification states the real RPO and the upgrade point rather than assuming enterprise guarantees.
  • Restore drill: quarterly, documented, with counts compared against expectations and logins verified.

15.10 Maintenance mode

A platform setting that: serves a maintenance page for the main app, keeps games reachable (they are separate deployments), blocks writes, keeps staff login available, and states an expected return time. Toggling it is an audited Owner or settings.manage action.
