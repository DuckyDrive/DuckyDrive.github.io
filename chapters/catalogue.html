Catalogue, Search & Discovery

Hosting status and project type are separate concepts. A project can be a site *and* a game, and a repository can exist without being deployed.

4.1 Project model

A single projects record backs every catalogue surface. Two independent axes describe it:

  • Type (what kind of project is it): Games, Sites, Software, Experiments, Repositories.
  • Hosting status (is it currently live): hosted, not_hosted, deployment_failed, unknown.

A project may carry several types. A browser game deployed to a path is Games + Sites. A library with no deployment is Software + Repositories. Filters treat the two axes independently, so "hosted games" and "repositories that are hosted" are different queries.

Categories are a controlled vocabulary managed by staff (Admin Panel → Catalogue). Tags are free-form but normalised: lowercase, hyphenated, max 24 characters, max 12 per project, with a blocked list for abusive or misleading terms. Both are many-to-many. Neither is ever used to mean hosting status.

4.3 Project detail page

Required blocks, in order:

  1. Name, type chips, hosting badge, latest version and update date.
  2. Artwork hero with a primary action: Play (hosted game), View site (hosted non-game), or View repository (not hosted).
  3. Description, then overview.
  4. Screenshots, keyboard-navigable gallery.
  5. Update history — version, date, changes, release notes, latest highlighted.
  6. Categories, tags, supported platforms.
  7. Creator/developer information and repository link.
  8. Release date, latest update date, discovery date.
  9. Favourite, follow, add-to-collection, report.
  10. Ratings summary and comment thread.
  11. Public statistics: plays, unique players where measured, followers, average rating, rating count.

Fields that cannot be verified are labelled "unavailable" rather than estimated silently. See Following and public statistics.

4.4 Launch behaviour

Selecting Play opens the game's own deployment full-screen at its path (/game-slug/), in the same tab by default with an optional "open in new tab" preference. There is no embedded iframe player as the default. The catalogue page encodes which deployment URL is authoritative, and only a validated, currently-live deployment receives a Play action.

4.5 Search

Search covers project name, description, tags, categories, creator name and platform. It is implemented as:

  • Server-side full-text search over a denormalised search document per project, weighted: name (A), tags/categories (B), description (C), creator (D).
  • Minimum query length of 2 characters; debounce 250ms; results paginated at 24.
  • Type-ahead suggestions limited to 8 items across projects and collections, keyboard navigable.
  • Filters applied server-side: type, category, tag, platform, hosting status, rating range, has-release-history.
  • Sorts: newest, recently updated, most popular, highest rated, most played, A–Z.
  • Empty results offer relaxed filters, not a dead end.

Rate limits: anonymous 30 searches/minute, authenticated 60/minute, with bursts accounted for by a token bucket.

4.6 Trending

Trending is not lifetime plays. It is a time-weighted engagement score over a 14-day window, recomputed hourly.

score = 0.45 * norm(recent_plays)
      + 0.20 * norm(recent_favourites)
      + 0.15 * norm(recent_ratings)
      + 0.10 * norm(recent_comments)
      + 0.10 * norm(growth_rate)

Each component is normalised per category so large categories do not dominate. growth_rate compares the current window with the previous one, capped to avoid a single spike owning the list.

Anti-abuse:

  • Plays are deduplicated by an opaque session fingerprint plus account, with a minimum 60-second gap counted once per hour per project.
  • Repeated refreshes do not create plays.
  • Rating and favourite bursts from new accounts carry reduced weight for the first 24 hours.
  • Accounts under enforcement do not contribute to engagement.
  • A metric with insufficient data is excluded from the score rather than defaulting to zero.

Trending exists overall and per category. Both are materialised so page loads never compute the ranking.

repository_created_at, release_date and discovered_at are three distinct fields and are never conflated. A ten-year-old repository added today appears in Newly added, not Recently updated.

4.8 Following and discovery lists

Following is a saved relationship, not a subscription: the Following list shows followed projects in update order, and no notification is produced when a followed project updates. Favouriting (a bookmark), following (interest), and adding to a collection (curation) are three separate actions with separate counts.

4.9 Recommendations and "Surprise me"

Personalised recommendations use categories of favourited and recently played projects, rating history, and similar-project signals (shared tags, same creator, similar category mix). Every recommendation list exposes a "why this" explanation.

Users can disable activity-based recommendations in Settings → Privacy. When disabled, the same surfaces render a non-personalised fallback: trending, newly added and staff picks. Disabling does not delete history; it stops that history being read for recommendations.

Surprise me selects from a validated, hosted, publicly visible pool using a weighted random pick that down-weights projects already shown this session. It never selects private, unvalidated or broken-deployment projects.

4.10 Discovery integrity

Every catalogue surface reads only projects where:

  • validation passed at least once and has not since failed,
  • visibility is public,
  • the source repository is public or the project was explicitly published by an authorised contributor,
  • the project is not hidden or unlisted by staff.

Automatic publishing (Chapter 8) supplies records; the catalogue is not a mirror of every repository in existence.
