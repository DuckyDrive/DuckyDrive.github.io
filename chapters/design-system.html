Chapter 03 · Sections 6-7

Design System, Navigation & UX

A dark, futuristic system with electric lime as the primary accent and neon purple as the secondary. Values here are proposed tokens, not previously approved values.

3.1 Colour tokens

Token Value Use
--bg-base #060910 Page background, near-black navy.
--bg-raised #0a0f1a Sections that sit above the base.
--panel #0e1626 Cards, sidebar, dialogs.
--panel-2 #121d31 Inputs, nested panels, hovered cards.
--line rgba(255,255,255,0.08) Dividers and card borders.
--line-strong rgba(255,255,255,0.14) Focused or emphasised borders.
--text #e8edf7 Primary text (cool white).
--muted #8e9bb3 Secondary text, metadata.
--muted-2 #66738c Tertiary text, placeholder.
--accent-lime #c6ff3d Primary actions, active state, success, primary links.
--accent-purple #a855f7 Secondary accent, featured labels, links in prose.
--danger #ff5f6d Destructive actions, destructive errors.
--warning #ffc857 Warnings, moderation states.
--info #4cc9f0 Informational banners.

Glow is used at low intensity: accent glows stay under 40% opacity, large radial glows only appear on hero surfaces, and no element uses more than one glow at a time.

3.2 Typography

Geometric display type for headings, a neutral sans for body, monospace for data.

Line length is capped at roughly 72 characters for prose. Numbers in tables and statistics use tabular figures so columns line up.

3.3 Spacing, radii and elevation

Spacing follows a 4px base: 4, 8, 12, 16, 20, 24, 32, 40, 48, 64. Radii: --r-sm: 10px (inputs, chips), --r-md: 16px (cards, panels), --r-lg: 24px (hero, modals), --r-full: 999px (pills, avatars).

Elevation is expressed as dark shadow plus border rather than light shadow, because the palette is dark:

  • --elev-1: 0 1px 0 rgba(255,255,255,0.04) inset
  • --elev-2: 0 18px 40px -24px rgba(0,0,0,0.8)
  • --elev-3: 0 32px 70px -32px rgba(0,0,0,0.9) plus a 1px --line-strong border

3.4 Interaction states

Every interactive element defines all six states. Missing states are defects.

State Treatment
Default Panel background, --line border, --text label.
Hover Background lifts one step, border becomes --line-strong, no layout shift.
Focus-visible 2px lime outline with 2px offset, always visible on keyboard focus; never removed without a replacement.
Active / pressed 1px translate down, background darkens slightly.
Disabled 45% opacity, cursor: not-allowed, no hover response, tooltip explains why when the reason is not obvious.
Loading Shimmer skeleton for content, inline spinner for buttons, button label replaced and aria-busy="true".

3.5 Feedback states

  • Empty — a short explanation, one primary action, no decorative illustration larger than the message.
  • Error — what failed, what to do next, and a retry action where retry is safe. Errors are announced to screen readers via role="alert" and are tied to fields with aria-describedby.
  • Partial — when one data source fails (for example GitHub metadata), show the catalogue entry with the missing field labelled "unavailable" rather than an empty page.
  • Offline / degraded — a persistent but non-blocking banner stating which feature is affected.

3.6 Application shell and navigation

Desktop shows a 286px left sidebar that collapses to a 72px icon rail. The rail keeps icons with tooltips and an accessible name on every item. Mobile replaces the sidebar with a slide-out drawer triggered by a menu button, closed by a scrim tap, the Escape key, or route change.

Navigation order (agreed areas): Home, Games, Sites, Repositories, Software, Newly Added, Recently Updated, Experiments, Trending, Following, Chat, Library, Settings. Admin Panel appears only for accounts holding at least one admin-scoped permission.

Search is available from the top bar on every route, opens with / or Ctrl/⌘+K, and returns grouped results (projects, collections, users, rooms). The sidebar keeps its own filter input for long chapter-style lists.

3.7 Homepage composition

  1. Hero — one featured project: artwork, name, one-line description, category chips, and a primary Launch/View action. Rotation is manual via arrow controls; there is no timer, no auto-advance and no rapid carousel.
  2. Continue — recently played, only when the user has history.
  3. Trending — the current 14-day trending list, category-filterable.
  4. Newly added — recent validated additions.
  5. Curated rows — featured collections or category picks.
  6. Discovery strip — search entry point plus "Surprise me".

3.8 Responsive behaviour

Breakpoint Width Layout
sm < 640 Single column, drawer nav, 16px gutters, 2-up card grid minimum 1-up.
md 640–1023 Two-column grids, drawer nav under 900px, 24px gutters.
lg 1024–1439 Expanded sidebar, 2–3 column grids.
xl ≥ 1440 Max content width 1280px, 3–4 column grids, sidebar stays expanded.

Cards reflow by container width, not by device guesswork. Sticky elements never cover more than 15% of viewport height on short screens.

3.9 Accessibility requirements

  • Semantic landmarks: header, nav, main, aside, footer, one h1 per route.
  • Focus order matches visual order; no positive tabindex.
  • Text contrast at least 4.5:1, large text 3:1, UI borders 3:1 against adjacent colour.
  • Minimum touch target 44×44px.
  • prefers-reduced-motion disables parallax, glow animation and carousel transitions.
  • Dialogs trap focus, restore focus on close, and have aria-modal with a labelled title.
  • Live regions announce async results (search counts, message arrival) without stealing focus.
  • Charts and statistic visuals have text equivalents.

3.10 Component inventory

Buttons (primary, secondary, ghost, danger, icon), inputs (text, search, select, multiselect, toggle, slider), chips, tabs, cards (project, collection, user, stat), project hero, rating control, comment thread, message bubble, toast, banner, modal, drawer, data table, pagination, skeleton, empty state, error state, permission badge, avatar stack.

Each component is specified once with its states and then reused. No route invents local variants of a shared component.

All values in this chapter are proposals for the design system. They are recorded as tokens so the implementation can apply them consistently rather than re-deciding on each screen.
