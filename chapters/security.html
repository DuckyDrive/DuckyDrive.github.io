Chapter 13 · Sections 32-34

Security, Privacy & Media Policy

The frontend is public and the backend is shared. Anything the browser can be tricked into sending is treated as hostile.

13.1 Threat model and mitigations

Threat Mitigation
Account takeover / credential stuffing Argon2id hashes, breached-password checks, per-account and per-IP throttling, second factor for staff, session list with revocation.
Session theft HTTP-only, Secure, SameSite=Lax cookies; short access tokens; refresh rotation with reuse detection; sessions bound to a device label.
CSRF Same-origin checks on every mutation plus double-submit tokens for cookie sessions; no state-changing GET.
XSS Output encoding by default; no dangerouslySetInnerHTML outside a sanitised Markdown subset; strict CSP with no unsafe-inline for scripts; no user HTML in profiles, comments or project copy.
SQL injection Parameterised queries only; no string-built SQL; RLS as a second layer.
Broken access control / IDOR Every object access re-checks ownership or membership server-side; client ids are never trusted as the subject.
Privilege escalation Permission grants are Owner-controlled, checked per request; no role inference; protected targets refuse modification.
Malicious project metadata Schema validation, URL scheme allowlist, path containment, plain-text rendering, never executed.
Malicious repository content Parsed as data only; no script execution during discovery; builds isolated in CI with minimal permissions.
Compromised webhooks HMAC signature verification over the raw body, delivery-id idempotency, replay window, rejected payloads logged.
Supply chain Lockfile pinning, dependency review, automated advisories, no postinstall scripts in build CI, least-privilege workflow tokens.
Build/deployment compromise Per-repository scoped tokens, protected branches, required reviews, environment protection, build output validated before publish.
Secret leakage Service-role keys only in function secrets; secret scanning in CI; no secrets in the client bundle; rotation runbook.
Spam and bots Rate limits, new-account friction, behaviour thresholds, CAPTCHA only on suspicious patterns.
XP / leaderboard manipulation Server-only scoring, immutable ledger, caps, anomaly detection, exclusions for enforced accounts.
Rating and follower brigading Weighting for young accounts, burst detection, per-account uniqueness, delayed public counts.
Fake plays Session fingerprints, duration thresholds, dedupe windows, outlier detection.
Chat abuse Rate limits, slow mode, mutes, report snapshots, moderation queue.
DLES abuse Capability manifests, per-action permissions, confirmations, audit, emergency stop, replay protection.
Reward duplication Unique (event_id, user_id, item) grants, idempotency keys, server-signed claims.
Denial of service Per-route quotas, pagination caps, query timeouts, bounded fan-out, caching for public reads, graceful degradation.

13.2 Headers and hardening

Content-Security-Policy with default-src 'self', explicit script/style/host allowlists for fonts and the API origin, frame-ancestors 'none', object-src 'none'. Plus Strict-Transport-Security, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy disabling camera, microphone, geolocation and payment.

Because game deployments are separate origins-by-path on the same host, the main application's CSP is scoped to its own routes so a game cannot weaken it, and games cannot read the platform's cookies beyond what the cookie scope allows.

13.3 Data minimisation

Collected: username, password hash, optional passkey/TOTP material, optional GitHub link, profile content the user chooses to add, activity needed for the features the user enables.

Not collected: email (unless a future product decision adds it as optional), real name, phone, address, precise location, IP addresses beyond short-lived hashed rate-limit keys.

Stored with care: IP hashed with a rotating salt for abuse detection and then discarded on a short schedule; user-agent reduced to a coarse device label; no third-party advertising or tracking scripts.

13.4 Privacy controls surfaced in the UI

  • Profile visibility, favourite visibility, collection defaults, online status, activity visibility.
  • Activity-based recommendations on/off, with a plain explanation of what is read and what is not.
  • Now-playing sharing, off by default, requiring integration support.
  • Notification categories, including the separate opt-in for game update subscriptions.
  • Data export (profile, collections, comments, ratings) and account deletion with a 14-day grace period.

13.5 Retention

Data Retention
Account and profile Until deletion (+14-day grace).
Sessions 30 days after last use, or on revocation.
Public chat messages 24 months.
Direct messages 12 months after last activity in the conversation.
Reports and snapshots 24 months after resolution, or longer where an appeal is open.
Moderation and audit records 36 months.
Security logs 12 months.
Aggregated statistics Indefinite, non-identifying.
Deleted-account identifiers in audit rows Retained as opaque ids, no personal data.

13.6 Media policy

Store Contents Rules
GitHub Source, game builds, static assets, release notes, project metadata and screenshots Public by definition; nothing secret is ever committed.
Supabase Storage Profile avatars and banners, small approved platform assets 2 MB max, JPEG/PNG/WebP, re-encoded, EXIF stripped, random keys, owner-deletable, moderated.
Chat Nothing Text, emojis and reactions only. No uploads, no attachments, no external-image workaround.

Game builds are not stored in Supabase Storage when GitHub Pages is the hosting target. Uploads are served through a controlled bucket with signed reads where the asset is private, and public reads only for published profile artwork.

13.7 Incident response

  1. Detect — error-rate alerts, failed-auth spikes, webhook failures, deployment failures, reports of abuse.
  2. Contain — revoke sessions, disable an endpoint via feature flag, put the platform in read-only or maintenance mode, revoke a leaked key.
  3. Assess — scope, affected data, whether notifications or legal obligations apply.
  4. Eradicate — patch, rotate secrets, invalidate tokens, remove malicious content.
  5. Recover — restore from backup if needed, verify integrity, re-enable features gradually.
  6. Review — written post-incident note with timeline, cause, and follow-up actions, stored with audit records.

Owner is notified of any security incident. Key rotation steps are documented and rehearsed, not improvised during an incident.

No claim of absolute security is made. The specification instead fixes the checks that must exist in code, the places where trust changes hands, and what the platform does when a control fails.
