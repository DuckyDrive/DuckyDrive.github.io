Chapter 11 · Sections 27-28

SDK & Live Events (DLES)

Games declare what they support. DuckyDrive never assumes a capability and never sends arbitrary code.

11.1 SDK scope

The DuckyDrive SDK is a JavaScript library with an extensible shape for future languages. It lets a game:

  • identify itself and its version to the platform,
  • report play sessions for statistics and XP eligibility,
  • declare supported capabilities,
  • receive authenticated event instructions from the backend,
  • acknowledge event actions and report status,
  • surface approved rewards through server-validated grants,
  • report compatibility so the platform can refuse unsupported features.

It does not let a game grant itself XP, rewards, staff powers, event permissions or limits. It does not accept remote code, injected scripts, or arbitrary client control instructions beyond declared capabilities.

11.2 Trust boundaries

Actor Trust Consequence
Browser game client Untrusted Can request; cannot decide. All rewards and XP validated server-side.
Game server (if present) Scoped credential Signs session and event acknowledgements; replay-protected.
DuckyDrive Edge Function Trusted Holds the service role, validates, writes the ledger.
Staff operator Authenticated + permission-checked Every action logged with reason.

Session reporting uses an idempotency key per session, an expiry, and a minimum duration before a play counts. Play counts are deduplicated against the session fingerprint, so refreshing a page does not inflate statistics.

11.3 Capability manifest

A game declares support in duckydrive.json and confirms it at handshake:

{
  "capabilities": {
    "sdk": "1.0",
    "playSessions": true,
    "liveEvents": ["announcement", "visual-weather", "audio-music", "reward-item"],
    "limits": { "maxParticles": 400, "maxEntitySpawns": 25, "maxAnnouncementSeconds": 30 }
  }
}

The platform keeps the declared list server-side. A DLES action for an undeclared capability is rejected with 422 capability_not_declared and never retried against that game.

11.4 DLES overview

DuckyDrive Live Events System lets authorised staff run global live events in supported games.

Confirmed behaviour:

  • Scope: global. An event applies to every active server of that game.
  • Scheduling: manual. Staff start and stop events. No automatic, recurring or cron-scheduled starts exist anywhere in the system.
  • Announcements: a banner at the top of the screen with chosen text, an approved colour for the announcement type, display duration, optional sound, and an optional countdown. Never a centre-screen takeover.
  • Audio: developer-approved tracks and effects only; volume, queueing, synchronisation with announcements, and a stop-all-audio control.
  • Visual effects: weather, lighting, particles, screen effects, environmental effects, fireworks, celebrations — all bounded by developer-declared intensity and duration limits, and restorable.
  • NPC/object spawning: allowed entity types, amount, location, behaviour presets and despawn timing within declared bounds.
  • Rewards: approved items, collectibles, currency, equipment or custom rewards; eligibility by all eligible online players, a specific player, or objective completion; duplicate-protected and audited.
  • Temporary player controls: approved teleport locations, temporary abilities, transformations, speed modifiers, event protection and team management. All expire automatically.
  • Emergency global stop is always available and immediately ends effects and audio.

Messages can be queued. Only capabilities the developer approved may be invoked. Admins cannot execute arbitrary code.

11.5 Coordinator architecture

Admin Panel (DLES module)
   │ start / action / stop  (staff auth + permission + confirmation)
   ▼
Event Coordinator (Edge Function)
   ├─ validates capability against manifest and current limits
   ├─ writes dles_events / dles_actions (queued)
   ├─ fan-out to active game servers (authenticated, ordered per event)
   ├─ collects acknowledgements, tracks per-server state
   ├─ retries idempotently with expiry on each action
   └─ writes audit + reward ledger entries

Rules the coordinator enforces:

  • An event id is unique and single-use; starting an already-active event is a 409, not a duplicate start.
  • Each action carries an idempotency key and an expiry; a late server receives the action only if it has not expired.
  • A server that disconnects mid-event is tracked as unreachable; on reconnect it receives the current event state and pending restorable actions.
  • A server that starts during an active event receives the current state on handshake, so events are globally consistent without replay storms.
  • Partial fan-out failures are reported per server and shown in the dashboard, with retry available per server.
  • Stopping an event while some servers are unreachable marks those servers pending_restore and continues retrying restore on a bounded schedule.
  • Rollback restores environment and temporary state where the game supports it; where it does not, the dashboard states the limitation rather than pretending.

11.6 Reward integrity

Rewards are written once per (event_id, user_id, item) — a database constraint, not a client check. High-impact grants (rare items, currency) require an explicit confirmation in the dashboard naming the target and quantity. Every grant records actor, event, target, item and timestamp. A reward claim from a game client is never trusted on its own; the game server signs the claim.

11.7 Permissions for DLES

dles.view, dles.announce, dles.audio, dles.visual, dles.spawn, dles.reward, dles.player_controls, dles.emergency_stop. Emergency stop is available to anyone with dles.view as a safety override, and is always logged with the actor.

11.8 Dashboard

Inside the Admin Panel — not a separate Developer Studio. Shows supported game, event state, live player count where the game reports it, per-capability controls gated by availability, queued actions, activity log, per-server status and the emergency stop. Unsupported capabilities appear disabled with the reason, so an operator never believes an action succeeded when the game never claimed it.

11.9 Freebuff workflow

When asked to add SDK support or DLES handling to a game, Freebuff reads this specification, adds only the required integration, updates duckydrive.json capabilities, runs the project's checks, and explains the changed files and risks. A human owner or contributor reviews and approves before publishing; GitHub Actions performs final checks and deployment. Freebuff never deploys on its own initiative.

Not every game can support every effect. A game that does not implement and declare a capability simply does not receive it, and the interface says so.
