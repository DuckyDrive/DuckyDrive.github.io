Chapter 14 · Sections 35-37

Performance, Accessibility & QA

Budgets that are measured, accessibility that is tested, and negative tests that try to break the permission model on purpose.

14.1 Frontend budgets

Metric Target (mobile, mid-range)
Largest Contentful Paint ≤ 2.5 s
Interaction to Next Paint ≤ 200 ms
Cumulative Layout Shift ≤ 0.05
Initial JS (compressed, per route) ≤ 180 KB
Fonts 2 families, subset, display=swap
Images AVIF/WebP, responsive srcset, lazy below the fold

Techniques: route-level code splitting, prefetch on hover/intent, artwork served at display size with an aspect-ratio box reserved, skeletons sized to final content, and no client-side blocking on analytics (there is none).

14.2 Backend and data budgets

  • Public catalogue reads served from materialised views with indexes on (visibility, discovered_at) and trending_score; no sequential scans on list endpoints.
  • Pagination capped at 50, default 24; no unbounded select *.
  • Query timeout 5 s for user-facing reads; heavy aggregation moved to scheduled jobs.
  • Realtime: one channel per open room, max 200 concurrent subscriptions per project page, presence throttled to one update per 30 s.
  • Background work (discovery scans, trending recomputation, snapshots, reconciliation) runs on a queue with concurrency limits and per-job timeouts.
  • Search: prepared full-text index; suggestions limited to 8 with a 250 ms debounce.
  • GitHub API: conditional requests, ETag caching, per-installation budget, jittered backoff.

14.3 Caching and degradation

Layer Policy
Static assets Immutable, hashed filenames, 1-year cache.
HTML entry Short cache with revalidation.
Public API reads Short-lived cache (30–60 s) with stale-while-revalidate.
User-specific data Never cached at shared layers.
Fallback If the backend is unreachable, show cached catalogue pages with a "may be out of date" banner; chat falls back to polling; GitHub failures surface as "unavailable" fields, not blank pages.

14.4 Accessibility requirements

  • Fully keyboard operable: skip link, landmark order, focus-visible on everything interactive, focus trapped in dialogs and restored on close.
  • Contrast: 4.5:1 body text, 3:1 large text and essential UI boundaries. Lime on near-black passes; lime text on light surfaces is never used.
  • Semantics: one h1 per route, headings in order, lists for lists, tables with headers and captions, forms with labels (not placeholder-only).
  • Announcements: aria-live="polite" for counts and toasts, assertive only for errors that interrupt.
  • Motion: prefers-reduced-motion removes parallax, glow animation and carousel transitions; no animation blocks input.
  • Touch targets: 44×44 px minimum, 8 px spacing between adjacent targets.
  • Zoom: usable to 200% without horizontal scrolling on a 375 px viewport.
  • Media: meaningful images have alt text; decorative artwork is marked decorative; charts have a text summary.
  • Games are out of scope for platform accessibility guarantees, but the catalogue states when a game's accessibility support is unknown.

14.6 Required negative tests

Each of these must fail safely, with a specific error and an audit entry where relevant:

  1. A normal member attempts an admin action → 403 permission_denied.
  2. An Administrator attempts an Owner-only action → 403, target protection holds.
  3. An Administrator without repository access attempts to edit a game → 403, even with every catalogue permission.
  4. A contributor loses GitHub access → next edit attempt fails, discovery scope shrinks.
  5. A private repository is discovered → withheld, never listed.
  6. A malformed duckydrive.json is found → validation error recorded, project not published.
  7. A webhook is replayed → second delivery is a no-op.
  8. A deployment fails → no public release entry, project marked deployment_failed.
  9. A DLES action is duplicated → second action rejected by idempotency.
  10. A game server disconnects during a global event → state tracked, restore attempted, dashboard shows unreachable.
  11. A user awards themselves XP or a duplicate reward → rejected by ledger constraint.
  12. A user uploads an image to chat → rejected by schema, not just hidden by the UI.
  13. A user requests another user's private collection or DM → 403 via RLS, not an empty response presented as success.
  14. A user follows a project and the project updates → no notification created.

14.7 Acceptance criteria pattern

Every feature carries its own criteria in Chapter 16, written as observable behaviour: given a state, when an action occurs, then a specific result. "Works well" and "is secure" are not criteria; "an unauthenticated POST to /collections returns 401 and creates no row" is.

14.8 Definition of done

A feature is done when: requirements and permissions are implemented, RLS is tested for all roles, error states exist, keyboard and screen-reader paths work, the relevant negative tests pass, audit entries are written where required, documentation is updated, and no confirmed decision from Chapter 2 is contradicted.
