Master Development Specification · v1.0

A gaming and project-discovery platform, specified end to end.

DuckyDrive is one unified application: a catalogue of games, sites, software and repositories, a username-only identity system, a GitHub-powered publishing pipeline, and a staff-run live events layer. This blueprint defines all of it before a line of product code is written.

Section 01Executive summary & vision

DuckyDrive is a place to find, play and follow games, websites, software experiments and source repositories. It combines four things usually sold separately: a discovery catalogue, a launch surface for games, a community layer, and a GitHub-powered publishing pipeline.

Discover

Browse, search, filter and get recommendations across games, sites, software, experiments and repositories.

Play

Games live in their own repositories and open full-screen from the catalogue — never inside an embedded player.

Belong

Accounts, profiles, friends, public chat, private messages, ratings, collections and leaderboards.

Publish

GitHub is the source of truth for source, releases and deployment; discovery is largely automatic.

Audiences

AudienceWhat they need from DuckyDrive
PlayersFind something good quickly, launch it in one click, track what they played and want to play.
Creators and contributorsPublish a project that updates itself from GitHub, without maintaining a separate site and catalogue entry.
Owner and staffOne Admin Panel for catalogue curation, moderation, announcements and live events.
Connected GitHub accountsConsent-based discovery of validated public projects, with editing rights tied to real repository permissions.

The one-application rule

Home, Games, Sites, Repositories, Software, Experiments, Newly Added, Recently Updated, Trending, Following, Chat, Library, Settings and the Admin Panel are views inside one application shell. They share one design system, session, router and backend. Games are the deliberate exception — separate codebases, separate deployments, separate paths on the same domain.

The consequence: "splitting Games into its own site" or "giving Chat its own domain" is never a valid implementation shortcut. If a section grows large, it is lazily loaded as a route inside the same shell.

Scope note. This is a planning document. It writes no application code, creates no platform repository, deploys nothing and configures no provider. Anything needing proof is recorded as a validation task, not presented as settled.

Explicit non-goals

  • A second developer dashboard for analytics, build logs or player funnels.
  • Any chat or DM attachment, including embeds that smuggle in external images.
  • Project-update notifications triggered by following.
  • Seasonal events, resets, or badges that expire with a season.
  • Automatic or recurring DLES schedules.
  • Separate hosted applications for Chat, Library, Settings or Admin.
  • A Developer role that grants game edit rights.
  • Required email collection, or a hidden email recovery path.
  • Embedded game players as the default launch behaviour.
  • Per-project discussion forums; comments and replies cover this.
  • Automatic deployment of private, unfinished, unsupported or unvalidated projects.

Assumptions to validate before commitment

  1. Username-only authentication can be implemented securely without a mandatory email identifier.
  2. Free-tier limits are sufficient for a prototype and early launch.
  3. GitHub Pages can host the main application plus many per-path game deployments.
  4. GitHub App permissions allow read-only discovery plus server-side permission checks.
  5. Webhook delivery is reliable enough for near-real-time updates.
  6. Realtime chat stays within connection and message quotas at expected concurrency.

Empty states explain and offer one action. Errors say what failed and what to do next, are announced with role="alert" and tied to fields. Partial failures label a field "unavailable" instead of blanking the page. Degraded mode shows a persistent, non-blocking banner naming the affected feature.

Application shell

Desktop: a 286px left sidebar that collapses to a 72px icon rail with tooltips and accessible names. Mobile: a slide-out drawer closed by scrim tap, Escape, or route change. Navigation order is Home, Games, Sites, Repositories, Software, Newly Added, Recently Updated, Experiments, Trending, Following, Chat, Library, Settings — with Admin Panel visible only to accounts holding an admin-scoped permission. Search lives in the top bar on every route, opens with / or Ctrl/⌘+K, and returns grouped results for projects, collections, users and rooms.

Homepage composition

  1. Hero — one featured project with artwork, name, one-line description, category chips and a Launch/View action. Rotation is manual; no timer, no auto-advance.
  2. Continue — recently played, only when history exists.
  3. Trending — the current 14-day list, category-filterable.
  4. Newly added — recent validated additions.
  5. Curated rows — featured collections and category picks.
  6. Discovery strip — search entry point plus Surprise me.
