Section 10Supabase, database & API contracts

Supabase is the planned backend, subject to prototype validation. The frontend is public, so every sensitive rule is enforced server-side.

GitHub Pages (public SPA)
   |  anon key, RLS-scoped reads
   +----> Supabase Postgres + RLS
   |          ^
   |          | service role (server only)
   +----> Edge Functions
            - auth adapter (username-only credentials)
            - GitHub webhook receiver
            - repository scan + validation jobs
            - XP / achievement awards
            - DLES coordinator
            - moderation + admin actions

Architecture constraints

  • The service-role key exists only in function secrets — never bundled, never in the repository, never a public variable.
  • The browser holds the anon key and can only do what RLS permits.
  • Every privileged operation is an Edge Function that authenticates, re-checks permissions against the database, then acts.
  • Client-supplied user ids, roles, XP totals, permissions and reward claims are ignored; the server derives them.
  • Separate dev, staging and prod projects with separate keys and data.

Identity without email

The planned adapter keeps credentials in a server-only table (password hash, passkeys, TOTP secrets), issues a short-lived signed session token on verification, and lets RLS read the verified subject claim — never a client-supplied id. Validating this adapter's security properties is a Phase 0 task. Fallback: a self-hosted session service with Supabase used for database, storage and realtime.

Database rules

  • Integrity: real foreign keys; cascade for dependent rows, set-null for retained public authors, restrict where moderation records would orphan.
  • Deletion: soft delete (deleted_at) for user-authored public content so tombstones and appeals work; hard delete for private data.
  • Counters: project_stats is the single source of public counts, updated transactionally and reconciled nightly.
  • Idempotency: uniqueness constraints, not client checks, for favourites, follows, ratings, likes, achievement grants, XP awards and DLES rewards.
  • Usernames: nothing references them; every foreign key uses ids.
  • Search: a materialised project search document with a full-text index, refreshed on change.
  • Migrations: numbered, forward-only SQL applied through CI, each with a documented compensating rollback.

Every endpoint documents its auth class (public, member, contributor, staff, owner, game-server), authorisation rule, validation, error codes, rate limit, idempotency behaviour and audit requirement. These are shape examples, not live service definitions.

Rate limiting is a token bucket per account and per IP at the function layer: auth 10/min, writes 30/min, search 60/min, reports 5/hour, DLES actions 20/min with confirmation on high-impact actions. Exceeding a bucket returns 429 with a retry hint; repeat abuse escalates to a temporary block and an audit entry.

Section 11SDK & live events (DLES)

The JavaScript SDK lets a game identify itself, report play sessions, declare capabilities, receive authenticated event instructions, acknowledge actions, surface approved rewards and report compatibility. It never lets a game grant itself XP, rewards, staff powers, event permissions or limits, and it accepts no remote code.

ActorTrustConsequence
Browser game clientUntrustedCan request; cannot decide. All rewards validated server-side
Game server (if present)Scoped credentialSigns session and event acknowledgements; replay-protected
Edge FunctionTrustedHolds the service role, validates, writes the ledger
Staff operatorAuthenticated + permission-checkedEvery action logged with a reason

Play sessions carry an idempotency key, an expiry and a minimum duration before a play counts, and are deduplicated against the session fingerprint so refreshes do not inflate statistics.

Capability manifest

{
  "capabilities": {
    "sdk": "1.0",
    "playSessions": true,
    "liveEvents": ["announcement", "visual-weather", "audio-music", "reward-item"],
    "limits": { "maxParticles": 400, "maxEntitySpawns": 25, "maxAnnouncementSeconds": 30 }
  }
}

The platform stores the declared list server-side. An action for an undeclared capability is rejected with 422 capability_not_declared and never retried against that game.

What DLES does

  • Scope is global: an event applies to every active server of that game.
  • Scheduling is manual: staff start and stop events; no automatic, recurring or cron-driven starts exist.
  • Announcements: a top-of-screen banner with chosen text, an approved colour per type, duration, optional sound and countdown — never a centre-screen takeover.
  • Audio: developer-approved tracks only, with volume, queueing, synchronisation and a stop-all control.
  • Visual effects: weather, lighting, particles, screen effects, fireworks and celebrations, bounded by developer-declared limits and fully restorable.
  • Spawning: allowed entity types, amounts, locations, behaviour presets and despawn timing within declared bounds.
  • Rewards: approved items or currency, eligible players by rule, duplicate-protected and audited — with confirmation for high-impact grants.
  • Temporary player controls: approved teleports, abilities, transformations, speed modifiers, event protection and team management, all expiring automatically.
  • Emergency global stop ends effects and audio immediately and is always available.

Coordinator behaviour

An event id is single-use: starting an active event returns 409, not a duplicate. Each action carries an idempotency key and an expiry, so a late server receives it only if still relevant. A server that disconnects during an event is tracked as unreachable and receives current state plus pending restorable actions on return. A server that starts during an event receives current state on handshake, keeping the event global without replay storms. Partial fan-out failures are reported per server with individual retry. Stopping while some servers are unreachable marks them pending_restore and retries on a bounded schedule. Rollback restores state where the game supports it; where it does not, the dashboard states the limitation instead of pretending.

Rewards are written once per (event_id, user_id, item) by database constraint, and a reward claim from a game client is never trusted alone — the game server signs it.

Dashboard and permissions

Inside the Admin Panel, showing supported game, event state, live player count where reported, per-capability controls gated by availability, queued actions, activity log, per-server status and emergency stop. Unsupported capabilities appear disabled with the reason. Permissions: dles.view, dles.announce, dles.audio, dles.visual, dles.spawn, dles.reward, dles.player_controls, dles.emergency_stop — the last available to anyone with view access as a safety override, always logged.

Section 12Admin Panel, staff & moderation

Deny by default. Three tiers. No Developer role. Every privileged action is checked server-side and logged.

TierGranted byScope
OwnerBootstrap onlyFull control; cannot be demoted, suspended or removed by other staff
AdministratorOwnerOnly explicitly granted permissions; starts with none until a preset or custom set is applied
ModeratorOwnerCommunity moderation only: chat, comments, reports, conduct

Game creation and editing belongs to the Owner and verified GitHub contributors — an Administrator without repository access cannot edit a game.

Permission presets

Full Administrator, Community Administrator, Game/Project Catalogue Administrator, Chat Moderator, Custom. Presets are convenience templates, not immutable roles.

Role labels never imply permissions; only grants do. No self-escalation exists: an Administrator cannot grant themselves anything or create another Administrator. Owner-only actions return 409 target_is_owner when aimed at the Owner and 403 when performed by a non-Owner. Grants are read from the database on every request, so changes apply immediately rather than at next login.

Panel modules

Users, Staff (Owner-controlled), Reports, Enforcement and appeals, Catalogue, GitHub integration health, Deployments, DLES, Announcements, Settings and feature flags, Audit log, and Health. There is no build studio, no per-game analytics dashboard and no code editor in the Admin Panel.

Moderation flow

  1. Report submitted with a category, optional note and an automatic snapshot of the target.
  2. Duplicate reports on the same target and category within 24 hours merge, raising priority.
  3. Queue ordered by severity, report count and target risk; automated triage flags obvious spam and new-account brigading.
  4. A moderator claims the report, locking it briefly to prevent double handling.
  5. Action: dismiss with reason, warn, mute, remove content, suspend or ban — each with a reason code.
  6. The target is notified where policy allows, with the reason category and appeal path; reporters learn the report was handled, not who did what.
  7. Appeals within 30 days, reviewed by a different staff member where one is available, with reasoning recorded.

Enforcement effects

EnforcementEffect
WarningRecorded; may restrict posting after repeats
MutePosting blocked until expiry; reading continues
SuspensionLogin for appeal only; no posting, no XP, off leaderboards, ratings excluded
BanSessions revoked; content hidden pending review; excluded from boards and public counts

Lifting enforcement restores participation immediately and restores aggregates at the next recalculation, audited. All staff require a second factor, staff sessions expire after 12 hours, and sensitive actions require a confirmation naming the exact consequence. Removing a staff member revokes grants and sessions, and the audit entry names the remover.

The audit log is append-only and server-written: actor, action, target, reason code, metadata (previous and new values where relevant), hashed IP and timestamp. Audit rows survive account deletion with the actor preserved as an immutable id, so history cannot be rewritten by deleting an account.
