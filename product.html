Section 04Catalogue, search & discovery

One project record backs every catalogue surface. Two independent axes describe it, and mixing them up is the most common modelling mistake in this kind of platform.

  • Type — what the project is: Games, Sites, Software, Experiments, Repositories. A project may carry several.
  • Hosting status — is it live: hosted, not_hosted, deployment_failed, unknown.

A browser game deployed to a path is Games + Sites. A library with no deployment is Software + Repositories. "Hosted games" and "repositories that are hosted" are different queries, and the filters treat them that way.

Categories and tags

Controlled game categories: Rhythm, Horror, Platformer, Multiplayer, Casual, Puzzle, Adventure, Racing, Sandbox, Other — multiple per game. Tags are free-form but normalised: lowercase, hyphenated, 24 characters maximum, 12 per project, with a blocked list for abusive or misleading terms. Neither is ever used to mean hosting status.

Project detail page

  1. Name, type chips, hosting badge, latest version, update date.
  2. Artwork hero with a primary action: Play, View site, or View repository.
  3. Description, then overview; screenshots in a keyboard-navigable gallery.
  4. Update history — version, date, changes, notes, latest highlighted.
  5. Categories, tags, supported platforms, creator information, repository link.
  6. Release date, latest update date, discovery date.
  7. Favourite, follow, add to collection, report.
  8. Ratings summary and comment thread.
  9. Public statistics: plays, unique players where measured, followers, average rating, rating count.

Unverifiable fields are labelled "unavailable" rather than estimated silently.

Search and sorts

Server-side search over name, description, tags, categories, creator and platform, weighted name > tags > description > creator. Two-character minimum, 250ms debounce, 24 results per page, eight grouped suggestions, filters applied server-side, sorts for newest, recently updated, most popular, highest rated, most played and A–Z. Rate limits: 30 searches/minute anonymous, 60 authenticated.

Trending

Never lifetime plays. A time-weighted score over 14 days, recomputed hourly:

score = 0.45 * norm(recent_plays)
      + 0.20 * norm(recent_favourites)
      + 0.15 * norm(recent_ratings)
      + 0.10 * norm(recent_comments)
      + 0.10 * norm(growth_rate)

Components are normalised per category so large categories do not dominate, and growth is capped so one spike cannot own the list. Anti-abuse: plays deduplicated by session fingerprint with a 60-second minimum and one count per hour, refresh spam ignored, young accounts' ratings and favourites down-weighted, enforced accounts excluded, and metrics with insufficient data omitted rather than scored as zero. Rankings are materialised; page loads never compute them.

Newly added versus recently updated

SurfaceOrdering basisNote
Newly addeddiscovered_atFilters for Games, Sites, Software, Repositories
Recently updatedLatest release timestampCommit fallback only when a project has no releases, and labelled

Repository creation date, release date and discovery date are three distinct fields. A ten-year-old repository added today appears in Newly added, not Recently updated.

Following, recommendations and Surprise me

Following is a saved relationship, not a subscription: the list shows followed projects in update order and never produces an update notification. Favouriting (bookmark), following (interest) and collecting (curation) are three separate actions with separate counts.

Recommendations use categories of favourites and recent plays, rating history and similarity signals, with a "why this" explanation. Users can disable activity-based recommendations; those surfaces then fall back to trending, newly added and staff picks. Disabling stops history being read for recommendations — it does not delete history.

Surprise me draws a weighted random project from the validated, hosted, publicly visible pool, down-weighting what the session has already shown, and never selecting private, unvalidated or broken deployments.

Section 05GitHub, publishing & deployment

Two discovery sources, one pipeline: repositories in the DuckyDrive organisation, and repositories of GitHub accounts that contributors explicitly connect. A GitHub username typed into a profile is never proof of identity or access.

Events

repository (create, delete, rename, transfer, visibility), release (published, edited, deleted, prerelease), push (meaningful activity when no release exists), a daily reconciliation scan, and manual resync.

Webhook handling: verify the signature on the raw body before parsing, persist the delivery id, make processing idempotent, process asynchronously with retries and a dead-letter record, handle out-of-order delivery by comparing timestamps against stored sync state, treat duplicates as no-ops, and track last_successful_scan so stale sync is visible to staff.

Passing projects publish automatically — there is no default approval queue. Repository content is untrusted input: discovery parses data, never executes repository scripts, and never runs a build. When a published project later fails validation it is withheld with its history preserved, removed from public surfaces within one refresh, and restored automatically when it passes again with its original discovery date.

Deployment model

https://duckydrive.github.io/            main application
https://duckydrive.github.io/game-one/   game one deployment
https://duckydrive.github.io/game-two/   game two deployment

Each game owns a repository and publishes only to /<its-slug>/, never to root. The slug is declared in metadata and reserved in the database. Assets must be relative (./assets/…); absolute /assets/… references are a validation error for games because they resolve to the main application. SPA fallback is per folder. Deployments are atomic, and a project is marked live only after GitHub Pages reports a completed build and a smoke fetch of the path returns 200 with the expected entry document.

Releases and update history

GitHub Releases are primary. Commit history is a labelled fallback only when a project has no releases. Drafts are ignored; prereleases are stored with a badge but never become "latest stable". Deleting a release removes it and recomputes the latest version, audited. A failed deployment never produces a public update entry. Every game page shows Update History with the newest entry highlighted.

Who may edit what

CapabilityRequired proof
Discover a repositoryPublic repository, or contributor consent for that repository
Edit project metadataOwner, or verified GitHub admin/maintain/push checked at action time
Trigger deploymentSame as edit plus explicit deployment permission
Hide or feature a projectStaff catalogue permission

Admin status never grants game editing on its own. Permission is re-checked per action rather than cached in a session, so a GitHub revocation takes effect immediately; the project stays published and attribution follows current collaborators.

Section 06The duckydrive.json standard

Every DuckyDrive game carries a small, versioned metadata file at its repository root. Freebuff creates and maintains it whenever a new game is started for DuckyDrive — including in a new chat — using only known information, and validates it before deployment. The user never has to repeat the instruction, and unrelated projects do not get the file.

Minimal valid file

{
  "schema": 1,
  "name": "Neon Drift",
  "description": "A one-button rhythm racer built for keyboard and touch.",
  "type": ["game"],
  "slug": "neon-drift"
}

Fully populated file

{
  "schema": 1,
  "slug": "neon-drift",
  "name": "Neon Drift",
  "description": "A one-button rhythm racer built for keyboard and touch.",
  "overview": "Longer copy shown on the project page.",
  "type": ["game"],
  "categories": ["rhythm", "casual"],
  "tags": ["one-button", "arcade", "synthwave"],
  "platforms": ["web", "mobile-web"],
  "thumbnail": "./art/thumb.png",
  "screenshots": ["./art/shot-1.png", "./art/shot-2.png"],
  "entry": "./index.html",
  "hosting": { "status": "hosted", "path": "/neon-drift/", "provider": "github-pages" },
  "repository": { "owner": "DuckyDrive", "name": "neon-drift" },
  "release": { "version": "0.4.1", "date": "2026-11-20", "notes": "Added two tracks and fixed touch input on iOS." },
  "featured": false,
  "capabilities": { "sdk": "1.0", "playSessions": true, "liveEvents": ["announcement", "visual-weather"] }
}

Errors and warnings

Errors block publication and name the failing path: E_SCHEMA_VERSION, E_REQUIRED, E_SLUG_FORMAT, E_SLUG_TAKEN, E_URL_UNSAFE, E_CATEGORY_UNKNOWN. Warnings never block: E_ASSET_MISSING (field dropped), W_TOO_LONG (truncated in listings), W_UNKNOWN_FIELD (preserved), W_NO_ENTRY.

Paths resolve inside the repository root and escapes are rejected; URLs must be https or repository-relative; the Markdown subset allows no raw HTML; and metadata can never declare permissions, roles or privileges. Unknown fields are preserved so a newer game can publish before the platform understands it. Schema changes ship with forward migrations, and both versions are accepted for at least one release cycle.

Section 07DuckyDrive ID, profiles & privacy

One account works across the ecosystem, with no mandatory email. Identity is a canonical user id (the only thing foreign keys reference), a unique and changeable username, credentials, ten single-use recovery codes, and optionally a linked GitHub identity.

Registration

  1. Username: 3–24 characters, a-z0-9_-, checked against reserved names, blocked terms and availability.
  2. Password: 12 characters minimum, checked against known-breached lists.
  3. Hash with Argon2id (bcrypt only if unavailable); never logged, never returned.
  4. Ten recovery codes shown once, stored only as hashes.
  5. Optional passkey or authenticator enrolment, explained in context.

Bootstrapping the Owner

The username DuckyDrive is reserved. The Owner account is never assumed to exist: a one-time bootstrap secret, held outside the repository, is exchanged for exactly one Owner account, then invalidated. If an Owner exists the endpoint refuses unconditionally. Every attempt is logged, success triggers an alert, and the Owner must enrol a second factor. The Owner cannot be demoted, suspended or removed by other staff.

Usernames and sessions

Changes are limited to once every 30 days, previous names are reserved for 180 days, lookalike names are rejected, and every change is logged. Sessions use HTTP-only, Secure, SameSite=Lax cookies with rotating refresh tokens; users see a session list with device labels and last-seen times and can revoke any session. Changing a password revokes all other sessions. Recovery-code regeneration invalidates every previous code after a confirmation warning. Rate limits and exponential backoff apply to login, recovery and registration.

Recovery honesty. With no email collected, an account that loses its password, passkey and recovery codes cannot be recovered automatically. The interface says so before registration and before codes are dismissed. Staff-assisted recovery is a narrow, audited, high-friction process — not a hidden email mechanism.

Profiles

Avatar, banner, changeable username, 500-character plain-text bio, join date, achievements, favourite projects, public collections, staff status when applicable, private-profile setting, visibility controls for favourites and collections, opt-in online status, and opt-out of "now playing". Avatar and banner uploads are separate from chat, which accepts no images at all: 2 MB maximum, JPEG/PNG/WebP, re-encoded, EXIF stripped, random object keys, owner-deletable, moderated.

ViewerPublic profilePrivate profile
AnyoneUsername, avatar, join date, public collections, achievementsUsername and avatar only

Blocking and deletion

Blocking is unilateral and immediate: both profiles hide from each other, friendship ends, requests and messages stop, and comments between the two hide. Deleting an account requires the password plus a second factor or recovery code, with a 14-day grace period. Personal data is removed or anonymised; public record content (comments, ratings, public collection metadata) is retained under a deleted-user placeholder unless removal is requested and no safety obligation applies. Moderation and audit records outlive the account, restricted to staff, and deletion logs never contain the deleted content.

Section 08Friends, chat, messaging & notifications

Text, emojis and reactions. No attachments in public chat or private messages, and no embedding workaround.

Friends and presence

Requests require a public profile or a shared room, max 20 pending outgoing, duplicates collapse to one row, and acceptance creates a symmetric friendship stored as a normalised pair. Blocking ends friendship, cancels requests and prevents posting between the two. Online status is opt-in and off by default, derived from recent authenticated activity with coarse labels; "now playing" requires both integration support and user permission.

Public chat

Rooms: General, Gaming, Development, Announcements. Guests read, members post. Rooms are created and archived under a staff permission; archived rooms become read-only. Messages allow 1,000 characters of plain text, emojis and reactions. Rate limit 5 messages per 10 seconds with a warning at 3 and a temporary mute for repeated bursts; duplicates collapse; slow mode can be enabled per room. Staff can remove messages (leaving a tombstone with a reason category), pin up to 10 per room, mute per room and review reports. Announcements is staff-post-only and also feeds the notification inbox.

Private messaging

  • Friend-only by default, or "nobody"; there is no open inbox. One-to-one only in v1.
  • Text, emojis and reactions — no images, video, files or external-URL embeddings.
  • "Delete for me" is local; "unsend" works for 10 minutes, replaces the message with a tombstone for both participants and keeps a moderation record without the body after 30 days.
  • Read receipts are off by default; when off, senders see only "delivered".
  • Blocking stops new messages; reporting includes context for moderators only.

Following a project never generates a notification. No code path converts a follow into an update notification; the game-update subscription is a separate, explicit action. Notifications deduplicate by a deterministic event key so retried jobs cannot double-notify, retain 90 days of history, and respect per-category quiet hours.

Realtime transport

One channel per open room, closed on route change; server-assigned sequence numbers for ordering with client reconciliation on reconnect; resume-from-sequence with up to 50 messages of backfill; a short-lived server-issued token encoding room membership so clients never choose their own identity; and a polling fallback every 10 seconds with a banner when realtime is unavailable. Messages are stored with author, room, body, timestamp, edit and moderation state; reports keep a snapshot so later edits cannot erase evidence. Retention: 24 months for public chat, 12 months after last activity for DMs.

Section 09Library, ratings & progression

Library surfaces: favourites, saved projects, recently played (30 items, private, clearable), achievements and collections. Favouriting, saving and following are three different actions with different privacy and counts.

Collections

Create, rename, edit, reorder and delete. Private by default, public on request; public collections are shareable, discoverable, followable and likeable, and show creator, item count, follower count and like count. Duplicates are prevented by a unique constraint rather than a client check. Ordering is explicit and reorderable by drag or keyboard. Deleting a collection cascades to items, follows and likes; making one private removes access immediately without notifying followers. Titles and descriptions are moderated.

Ratings and comments

One 1–5 star rating per account per project, editable and deletable, with materialised average and count updated in the same transaction. A written comment is optional and independent; comments support two levels, likes, reports and a single marked creator reply. Anti-brigading: ratings from accounts younger than 24 hours, or with no play session on a game, are recorded but weighted zero in the displayed average until the account ages, and the interface says when a rating set is adjusted. Removed comments leave tombstones. Deleted accounts lose their ratings; suspended accounts are excluded while enforcement lasts and restored if it is lifted cleanly.

Aggregates never change silently. Every recalculation driven by moderation or enforcement writes an audit row with project, old value, new value, reason, actor and timestamp.

Achievements and XP

Families: Explorer, Player, Collector, Critic, Creator/Contributor, Veteran. Tiers: Bronze, Silver, Gold, Diamond. XP is awarded once per achievement, enforced by a unique constraint, and written to an append-only ledger from which balances and levels derive. Daily caps per family prevent grinding; self-dealing is blocked; suspended accounts earn nothing and leave the boards; rewards are cosmetic only — no gameplay advantage, no purchases.

RiskMitigation
XP farmingDaily caps, diminishing returns, unique grants
Bot playsSession fingerprints, minimum duration, anomaly detection
Rating brigadingNew-account weighting, one rating per account, burst detection
Follower inflationYoung-account follows excluded from public counts until aged
Duplicate rewardsUnique grants plus idempotency keys

Leaderboards

Global XP, weekly, monthly, level ranking and a contributor ranking based on validated published work. Weekly and monthly are rolling windows, not seasons: no reset ceremony, no seasonal badges, no pass. Contributor ranking measures published work, not permissions, and creates no staff role. Snapshots are materialised hourly and daily; ties break by earliest achievement then account age; banned accounts are removed at the next snapshot, and the removal is logged.
